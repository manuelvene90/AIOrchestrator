## 1. Claude Code headless/programmatic surface (CLI) vs. Claude Agent SDK

### 1.1 The installed CLI's actual flag surface (v2.1.263, verified live)

Full `claude --help` output was captured directly (see command run this session). Key flags, quoted exactly:

**Present and match the brief:**
`--resume`/`-r [value]`, `-c`/`--continue`, `--fork-session`, `--session-id <uuid>`, `--output-format <format>` (`text`, `json`, `stream-json`), `--input-format <format>` (`text`, `stream-json`), `--include-partial-messages`, `--json-schema <schema>`, `--max-budget-usd <amount>`, `--autocompact <auto|tokens>`, `--settings <file-or-json>`, `--strict-mcp-config`, `--mcp-config <configs...>`, `--append-system-prompt <prompt>`, `--system-prompt <prompt>`, `--allowedTools`/`--allowed-tools <tools...>`, `--permission-mode <mode>` (choices: `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan` — note: no bare `default` in the choice list shown), `--agents <json>`, `--betas <betas...>`, `--disable-slash-commands` (help text: "Disable all skills" — the flag name and its own description disagree; treat the description as authoritative), `--no-session-persistence`, `--fallback-model <model>`, `--include-hook-events`, `--forward-subagent-text`.

**Present but NOT in the brief's list (new/renamed since older docs):**

- `--bg`/`--background`, plus top-level commands `agents`, `attach <id>`, `logs <id>`, `stop|kill <id>`, `rm <id>`, `respawn [options] [id]` — a **native background-session manager** (see §1.4).
- `--bare` (minimal boot: skips hooks/LSP/plugin sync/auto-memory/keychain), `--restricted` (removes Bash/PowerShell/code-exec tools and WebFetch unless named, ignores project/local settings), `--safe-mode`, `--exclude-dynamic-system-prompt-sections` (moves cwd/env/git-status out of the system prompt into the first user message specifically to **improve cross-session prompt-cache reuse**), `--system-prompt-snapshot <on|off>`, `-w`/`--worktree`, `--from-pr`, `--cloud`, `--environment <ccpool_...>`, `--teleport`, `--tmux`, `--prompt-suggestions`.
- `ultrareview` — a **cloud-hosted multi-agent code review** subcommand that runs against the current branch/PR/base branch.

**Absent from the installed CLI (contrary to the brief's assumption / to what older docs and third-party guides describe):**
- **`--max-turns` does not exist on this binary.** `grep -i turn` on the full help output returns zero flag matches (only unrelated substrings like "return" and "turn" inside other flags' descriptions). Third-party 2026 cheat-sheets still list `--max-turns` [unverified against a live CLI — those pages could not be confirmed against 2.1.263]. `maxTurns`/`max_turns` **does** still exist as an Agent SDK option (confirmed in the SDK docs, e.g. the fork-session example passes `max_turns: 5`) — so turn-capping is an SDK-only knob now, not a CLI flag, on this version. **This is a real gap for a daemon that shells out to the CLI**: nothing stops a headless `claude -p` turn from running an unbounded number of tool-call turns except `--max-budget-usd` (dollars) or a hook.
- **`--permission-prompt-tool` does not exist as a top-level flag**; superseded by `--permission-prompts host|none` (source: local `--help`).
- `CLAUDE_CODE_AUTO_COMPACT_WINDOW` is not a CLI flag (it's an env var, see §3), but it **takes precedence over** `--autocompact`, the `/autocompact` command, and the `autoCompactWindow` settings key, in that stated order (source: `code.claude.com/docs/en/env-vars`, `code.claude.com/docs/en/model-config`, via context7, fetched 2026-09-08). `--autocompact` accepts `auto`, a plain token count, `k`/`M` suffixes, or a bare 100–1000 number meaning thousands, clamped to 100K–1M tokens.

### 1.2 What the JSON result carries (`--output-format json`)

Per `code.claude.com/docs/en/sessions` and `.../headless` (context7, fetched 2026-09-08) and corroborated by third-party guides: the single JSON result includes `result` (the final text), `session_id`, `total_cost_usd`, and a `metadata`/usage block. The `/usage` in-session command (a different surface, interactive) shows the same shape of data the JSON result draws from: per-model input/output/cache-read/cache-write token counts and a computed list-rate cost, e.g.:
```
claude-sonnet-4-6:  1.2k input, 5.3k output, 940.0k cache read, 50.0k cache write ($0.55)
```
(source: `code.claude.com/docs/en/costs`, via context7). This is the direct, structured equivalent of what AIOrchestrator currently gets by scraping the statusline `.usage.json` — see §4.

`stream-json` emits newline-delimited events in real time (`--include-partial-messages` adds partial chunks; `--include-hook-events` adds hook lifecycle events into the same stream; `--replay-user-messages` echoes stdin user messages back out for ack, only paired with `--input-format stream-json` + `--output-format stream-json`) — source: local `--help` + `code.claude.com/docs/en/headless` (context7).

### 1.3 Claude Agent SDK (TypeScript/Python) — what it adds over the CLI

Confirmed via context7 (`/websites/code_claude_en_agent-sdk`, `code.claude.com/docs/en/agent-sdk/*`, fetched 2026-09-08):

- **`query(prompt, options)`** is the entry point in both languages; it wraps the same Claude Code harness the CLI uses (it is literally "Claude Code packaged as a library" per the `claude-api` skill's own disambiguation note, which is worth trusting since it's Anthropic's own skill content).
- **`resume`** + **`forkSession`/`fork_session`**: forking branches *conversation history only, not filesystem state* — documented explicitly: "forking branches conversation history only, not filesystem modifications" (`code.claude.com/docs/en/agent-sdk/sessions`). This matters for AIOrchestrator's "fresh session per turn" idea — a fork does not give you a clean working tree.
- **`sessionStore`** (e.g. `InMemorySessionStore`) — pluggable session persistence; the SDK docs explicitly note that "Connection or process errors do not yield a result message, while query error results throw after yielding" — i.e., a daemon polling for `session_id` must distinguish "no result message" (process/connection failure — no session captured) from "error result" (session_id was captured, but the turn itself failed). This is a concrete correctness detail AIOrchestrator's C# wrapper around the CLI should mirror when parsing stream-json/JSON output.
- **Hooks run in-process** — same event names as the CLI's hook system (`PreToolUse`, `PostToolUse`, `Stop`, `SessionStart`, `SessionEnd`, `UserPromptSubmit`, plus the fuller list in §5) but as **callback functions**, not subprocesses. A `HookMatcher` scopes a hook to a tool-name pattern; return shape is the same `hookSpecificOutput` JSON envelope the CLI's shell-hook protocol uses (`permissionDecision`, `additionalContext`, etc.) — so the wire format is shared between CLI hooks and SDK hooks even though the SDK ones don't fork a process.
- **`canUseTool`**: a permission callback for session-specific policy, layered under hooks for universal invariants (source: WebSearch synthesis citing Anthropic SDK guidance) — `[documented, secondary source]`, i.e. I could not get the primary `agent-sdk` page to state this exact division of labor verbatim, but it is consistent with the hooks-vs-`canUseTool` framing in multiple current guides.
- **`settingSources`**: controls whether project/user/local settings files (CLAUDE.md, `.claude/settings.json`, hook definitions, etc.) load at all — the hooks page notes shell-command hooks from settings files only fire "when the corresponding `settingSources`/`setting_sources` entry is enabled, which it is for default `query()` options" (`code.claude.com/docs/en/agent-sdk/hooks`).
- **Structured outputs**: `output_format={"type": "json_schema", "schema": {...}}` on `ClaudeAgentOptions`, surfaced on the result message as `structured_output` (Python example, `code.claude.com/docs/en/agent-sdk/structured-outputs`). This is the SDK-side equivalent of the CLI's `--json-schema`.
- **`maxBudgetUsd`**: numeric budget option in `query()` options (WebSearch synthesis; consistent with the CLI's `--max-budget-usd`, which the help text notes "only works with --print").
- **In-process custom tools / in-process MCP servers**: not directly re-verified with a primary quote in this pass, but this is Anthropic's stated differentiator for the SDK over shelling out (per the `claude-api` skill's own comparison table: the Agent SDK "ships built-in tools... the full agent loop, context management, hooks, subagents, permissions, and sessions" and both Tool Runner and Agent SDK are "harness-only — you host and deploy them").

### 1.4 Is there a .NET SDK? Shelling out vs. embedding — the actual answer

**There is no official Anthropic Agent SDK for .NET/C#.** Confirmed two ways:
1. Context7's own library resolution for "Claude Agent SDK" returns exactly two Anthropic-owned repos — `/anthropics/claude-agent-sdk-python` and the TypeScript one (mirrored under `/websites/code_claude_en_agent-sdk`) — plus **one community/unofficial** result, `/0xeb/claude-agent-sdk-dotnet` ("a modern .NET library for interacting with Claude Code CLI, providing one-shot API and full bidirectional client support with control protocol, hooks, and MCP server capabilities" — note the description itself says it wraps the **CLI**, i.e. it's a subprocess wrapper, not a from-scratch .NET port of the harness).
2. WebSearch (2026-09-08) confirms Anthropic **does** ship an official C# SDK — package name `Anthropic` on NuGet, docs at `platform.claude.com/docs/en/api/sdks/csharp` — but that SDK is for the **raw Messages API** (`POST /v1/messages`), the same tier as the Python/TS `anthropic` package, **not** the Agent SDK / Claude Code harness. It gives you `client.messages.create(...)`, not built-in tools, a coding-agent loop, hooks, or sessions.

**Implication for AIOrchestrator**: shelling out to the `claude` CLI (what the daemon already does) is not a stopgap while waiting for a "proper" SDK — it **is** the only first-party-adjacent path for a .NET host today. The three options the brief named:
- **Sidecar Node/TS process running the real Agent Agent SDK** — gains in-process hooks, `canUseTool`, structured-output validation, and typed session objects, at the cost of an inter-process boundary between C# and Node (gRPC/HTTP/stdio) that the daemon doesn't currently have. Only worth it if the daemon needs SDK-only features (in-process custom tools/MCP servers, `sessionStore` abstractions) that CLI flags can't reach.
- **The unofficial `claude-agent-sdk-dotnet`** — still shells out to the CLI under the hood per its own description, so it buys ergonomics (typed control-protocol client, hook plumbing) without changing the underlying transport. Unofficial = no support guarantee, and it should be read/audited before trusting it in a daemon that touches production-adjacent workflows.
- **Keep shelling out directly** (current approach) — `-p --resume <id> --output-format stream-json` already exposes session IDs, cost, hooks (as subprocesses), and MCP config via flags/JSON files. The main things a raw CLI shell-out cannot get that the SDK can: in-process custom tools (must instead go through MCP servers, which is already the CLI's own extension mechanism, so this is a smaller gap than it looks), and typed compile-time session/result objects (mitigated by writing one narrow C# DTO layer over the JSON result/stream-json events once).

**Verdict**: no architecture change is justified by "there's a better SDK we're missing" — there isn't one for .NET. The gap that *is* real is `--max-turns` not existing at the CLI level (§1.1) and the need for a disciplined DTO layer over stream-json (§1.2/1.3) — both addressable without adopting Node.

## 2. Multi-agent primitives: Agent Teams, subagents, background agents

### 2.1 Agent Teams (`code.claude.com/docs/en/agent-teams`, fetched 2026-09-08, "as of v2.1.178")

Agent Teams is **experimental and disabled by default**, gated by `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. Architecture: a **team lead** (the main session) spawns **teammates**, each a full separate Claude Code instance with its own context window; they coordinate via a **shared task list** (pending/in-progress/completed, with dependencies) and a **mailbox** — literally a JSON file per agent at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`, delivered by the `SendMessage` tool. `TeamCreate`/`TeamDelete` **tools no longer exist** as of v2.1.178 — team setup/teardown is now automatic, session-derived (`team-name = "session-" + first 8 chars of session ID`).

**The single most important finding for AIOrchestrator: Agent Teams cannot run headless.** Verbatim from the docs: *"Spawning teammates also requires an interactive session. In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates, and a subagent that Claude names runs as an ordinary subagent even with agent teams enabled."* Since AIOrchestrator's entire model is headless `claude -p --resume` turns driven by a .NET daemon, **Agent Teams is architecturally inapplicable as-is** — it's built for an attended terminal session with a TUI agent panel, tmux/iTerm2 split panes, and a human approving plans. This directly answers the brief's question 2: a supervisor/implementer/reviewer topology is **not** expressible via native Agent Teams under this product's headless constraint, full stop — not "expressible but lossy," genuinely unavailable.

Other documented limitations relevant even for a hypothetical interactive fallback: **one team per session, no nested teams** ("teammates cannot spawn their own teammates. Only the lead can manage the team"), **no session resumption for in-process teammates** (`/resume`/`/rewind` don't restore them), lead is fixed for the session's lifetime, permissions are set once at spawn (can't set per-teammate mode at spawn time), and — cost — "Agent teams use significantly more tokens than a single session... token usage scales with the number of active teammates," with the docs explicitly recommending single-session/subagents instead for "sequential tasks, same-file edits, or work with many dependencies." There's also a caching wrinkle: an in-process teammate's requests fall **outside** the main conversation's cache-TTL bucket, so by default its cache only holds 5 minutes even on a subscription plan that would otherwise get an hour, unless `subagentPromptCacheTtl` is explicitly set to `1h` (which bills 1-hour cache writes at 2× — see §3).

**What AIOrchestrator's current design already reproduces, natively-inspired but process-level:** hub-and-spoke topology with one channel file per pair (→ Agent Teams' one-mailbox-per-agent JSON file, same idea, one level up); append-only markdown channel (→ Agent Teams' mailbox JSON, less structured but the same "durable local file as the coordination bus" idea); watcher-wakes-on-append (→ Agent Teams' "delivered automatically... the lead doesn't need to poll"). The product's architecture decision 3/4 (central channel home outside git, hub-and-spoke, one file per implementer) is functionally a from-scratch reimplementation of what Agent Teams does *inside one interactive process* — done instead across **separate OS processes**, which is the only way to get it headless, phone-mirrorable, and per-role-model-priced today.

### 2.2 Cross-session messaging — a lighter native primitive, but its headless status is unverified

Separate, non-experimental-labeled feature (`code.claude.com/docs/en/cross-session-messaging`, `whats-new/2026-w32`, v2.1.224+, macOS/Linux): lets one Claude Code session send a **plain-text** message to another session on the same machine, a different machine, or the web, via a `SendMessage`/`ListAgents` tool pair. Explicitly scoped down from Agent Teams: "Incoming messages do not grant permissions, execute slash commands, or transfer file/history context" and messages "do not include full conversation histories or files." `crossSessionInbound` setting controls accept/hold/refuse. **I could not find a primary-source statement on whether this works from a headless `-p` session** the way Agent Teams explicitly does not — the docs describe it in terms of interactive sessions and a `/list-agents` command. Mark this `[unverified]` and worth a 10-minute live test before building on it; if it does work headless, it is a closer native analogue to the markdown-channel-file pattern than Agent Teams, since it's built for exactly "tell the other active session X" without the interactive-TUI baggage.

### 2.3 Subagents (single-session, in-process)

Distinguished from Agent Teams by the docs' own comparison table: subagents have "own context window; results return to the caller," are spawned/managed entirely by the main agent (no self-coordination), and are "Lower [cost]: results summarized back to main context." Subagents **do** work in headless/SDK mode (Agent Teams explicitly does not). `--agents <json>` on the CLI defines them inline (e.g. `'{"reviewer": {"description": "Reviews code", "prompt": "..."}}'`) with per-subagent model selection via `CLAUDE_CODE_SUBAGENT_MODEL` / `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` env vars (source: agent-teams doc's "Specify teammates and models" section, which states the same model-selection precedence applies to teammates *and* subagents).

### 2.4 Background agents — the CLI feature that's actually relevant here

Not named in the brief, but directly load-bearing: v2.1.263's CLI ships a **native background-session manager** — `--bg`/`--background` starts a session and returns immediately, printing an id; `claude agents` lists them; `claude attach <id>` reopens one in a terminal; `claude logs <id>` prints recent output; `claude stop|kill <id>` stops one (conversation kept, resumable); `claude rm <id>` deletes one; `claude respawn [id|--all]` restarts a background session "so it runs the current Claude Code version." This is functionally close to what AIOrchestrator's daemon builds by hand today (spawning terminal processes, tracking PIDs, respawning dead ones per architecture decision 8's `SessionWatchdog`). **Worth evaluating directly**: does `claude --bg` + `claude logs`/`attach`/`respawn` replace the daemon's own process-spawn-and-pidfile-tracking logic, or does the daemon need capabilities (per-role env injection, custom terminal titles, WT-specific window management for the phone-mirroring/"show session" UX) that this native feature doesn't cover? This is a concrete follow-up worth a scoped spike rather than a full section here since it wasn't in the original 5 research questions, but it's the single highest-leverage "native alternative" this research surfaced.

### 2.5 MCP-based coordination

Not separately verified beyond what's already implicit in §1.3 (in-process MCP servers) and the fact that both hooks and Agent Teams already give you file-based coordination primitives. An MCP server as a coordination bus would mean building and hosting a stateful MCP server the daemon and every session all point at — strictly more infrastructure than the current channel-file approach for no protocol benefit already offered natively (mailbox JSON, cross-session messaging). Not recommended as a distinct path.

## 3. Context/memory engineering evidence

### 3.1 Anthropic's own guidance (`anthropic.com/engineering/effective-context-engineering-for-ai-agents`, Sept 2025, fetched via WebFetch 2026-09-08)

Frames context as a "finite, precious resource" with diminishing marginal returns — the core mechanical reason given is architectural: transformer attention creates *n²* pairwise relationships for *n* tokens, so as context grows "the model's ability to capture these relationships gets stretched thin," and even well below a stated context-window ceiling, models "start to summarize, externalize notes, and close tasks early when they think they're near the edge." Three concrete techniques, each with a verbatim quote:
- **Compaction**: "distills the contents of a context window in a high-fidelity manner, enabling the agent to continue with minimal performance degradation" — implementation guidance is recall-first, then trim redundant content (repeated tool outputs) for precision.
- **Structured note-taking**: persistent memory *outside* the context window — to-do lists, `NOTES.md`-style files — so an agent can "track progress across complex tasks, maintaining critical context and dependencies" across dozens of tool calls. This is a direct, primary-source endorsement of exactly the "small STATE block" idea in the brief's proposal.
- **Sub-agent architectures**: lead agent keeps strategy, sub-agents do deep work in clean context windows and return **condensed summaries, typically 1,000–2,000 tokens**, not full exploration logs — a concrete number worth designing AIOrchestrator's implementer→supervisor reporting around.
- No numeric compaction trigger threshold is given in this post; the closest anchor to a number is elsewhere in the product docs — the **default `autoCompactWindow` is model-tuned, and the CLI's own error text uses 150,000 tokens as a reference figure for a 200K-context model** ("the compact-2026-01-12 beta's default trigger threshold" per the `claude-api` skill content — [documented, secondary confirmation]), and `autoCompactWindow`/`--autocompact`/`CLAUDE_CODE_AUTO_COMPACT_WINDOW` all accept 100K–1M explicitly (§1.1).

### 3.2 "How we built our multi-agent research system" (`anthropic.com/engineering/multi-agent-research-system`, fetched 2026-09-08)

Directly quantifies the "fresh, clean-context subagent" pattern AIOrchestrator already uses for implementers: **"multi-agent systems use about 15× more tokens than chats"**; plain **agents use about 4× more tokens than chat**; the lead-vs-subagent (Opus 4 lead + Sonnet 4 subagents) architecture **"outperformed single-agent Claude Opus 4 by 90.2%"** on their internal research eval; and — the single most load-bearing number for cost/quality tradeoffs — **"token usage by itself explains 80% of the variance"** in outcome quality, with model choice and tool-call count splitting the remaining ~15–20%. Design guidance: the lead uses **extended thinking** for planning and an **external memory** specifically to survive conversations that exceed 200,000 tokens (i.e., its own context-loss mitigation is memory-to-disk, not a bigger context window); subagent count scales 1 (simple query) to 10+ (complex research); subagents get "objective, output format, guidance on tools and sources, and clear task boundaries" (this is essentially a spec for what a supervisor's brief to an implementer should contain); parallel tool calls (3+ concurrently) cut completion time up to 90%.

### 3.3 Context rot (Chroma Research, `trychroma.com/research/context-rot`, July 2025, per WebSearch synthesis 2026-09-08 — I did not get a primary WebFetch of the Chroma page itself in this pass, treat the following as `[documented, secondary source: multiple aggregator summaries agree]`)

Tested 18 frontier models including Claude Opus 4; found performance degrades with input length **even when the window isn't close to full** — i.e., "context rot" is not merely a hard-limit problem. The "lost-in-the-middle" effect (attention favors context start/end, degrades in the middle) is cited as causing 30%+ accuracy drops in some configurations; the reason given is the same quadratic-attention mechanic Anthropic's own post cites (100K tokens ≈ 10 billion pairwise token relationships). **Direct implication for AIOrchestrator's measured 249K-token median first-call context, 690K/turn**: those figures are not merely expensive in dollars — per this research they are also inside the range where model *quality*, not just cost, degrades, independent of whether the 1M window has headroom left. This strengthens the case for "fresh session + digest" over "keep resuming one long transcript," on quality grounds, not only cost grounds.

### 3.4 Prompt caching economics — primary source (`platform.claude.com/docs/en/build-with-claude/prompt-caching`, fetched via WebFetch 2026-09-08)

Exact multipliers, quoted:
> "5-minute cache write tokens are 1.25 times the base input tokens price; 1-hour cache write tokens are 2 times the base input tokens price; Cache read tokens are 0.1 times the base input tokens price (see the table footnote for per-model exceptions)."

Per-model exception: Claude Fable 5.1 / Mythos 5.1 cache reads price at **0.025×** base input instead of 0.1×. **Default TTL is 5 minutes.** Minimum cacheable prefix varies 512–4,096 tokens by model tier (Opus 5/Fable 5 family: 512 tokens; Sonnet 5/Opus 4.8/Sonnet 4.6 family: 1,024; Opus 4.7/Haiku 3.5: 2,048; Opus 4.6/Haiku 4.5: 4,096) — shorter prefixes silently don't cache, no error. This confirms the measured `cache_read = 97.8% of tokens` figure in the brief is operating at the **0.1× rate** (or 0.025× if the daemon is on a Fable/Mythos model), i.e. that 97.8% figure, at 0.1× pricing, is worth roughly 9.78% of a full-price-equivalent token bill for that share — a very large share of nominal "cost" is actually ~90%-discounted, which changes how the team should read the raw token counts in `.usage.json`: **token count alone overstates cost by roughly 10× on the cached share** unless the reader already applies the multiplier. This is a concrete bug-risk in "plan-consumo-token"-style ledgers that count raw tokens without weighting by cache-read discount.

A `[unverified]` secondary claim from several 2026 blog posts (not confirmed against Anthropic's own page in this pass, and contradicted by the primary page above which states the *current* default is 5 minutes without qualifying it as a change): that the default TTL was **changed from 1 hour to 5 minutes in early 2026**. Treat this as plausible context for why older docs/tutorials assume 1-hour caching, but don't cite it as an Anthropic-confirmed migration date without checking Anthropic's changelog directly.

### 3.5 Do cached tokens count toward the weekly usage limit?

**Not confirmed either way with a primary source in this pass.** WebSearch aggregation (2026-09-08, multiple third-party "Claude Code limits" explainer sites, none of them Anthropic's own docs) states that on the **API rate-limit side**, "cache read tokens do not count toward ITPM (input tokens per minute); cache creation and uncached input do" — but none of the sources I could reach directly addressed whether the **subscription weekly/5-hour usage window** (the one the statusline's `rate_limits.seven_day`/`five_hour` fields report, §4) applies the same cache-token exemption. Given decision 10 in the project's own CLAUDE.md flags this as "NEEDS LIVE VERIFICATION," this research does not close that gap — it should still be verified against a live account, ideally by triggering a heavy-cache-read turn and watching whether `rate_limits.five_hour.used_percentage` moves proportionally to raw tokens or to a cache-discounted figure. Recommend: don't build alerting math on an assumption here; measure it once directly.

Applying §3.4's multipliers to Sonnet 5 (the plausible implementer/supervisor model given the product's cost-consciousness): a fully-cached 690K-token turn at $2/1M input, 97.8% cache-read, would cost roughly `690K × (0.978×0.1 + 0.022×1.0) × $2/1M ≈ $0.165` for the input side alone (excluding output tokens and any cache-write cost on the ~2.2% fresh portion) — versus a naive "690K tokens × $2/1M = $1.38" reading that ignores caching entirely. **Any cost dashboard or ledger reading `.usage.json` raw token counts without this weighting will overstate spend by roughly 6–8× on heavily-cached turns.**

## 4. Telemetry/cost

### 4.1 OpenTelemetry export (`code.claude.com/docs/en/monitoring-usage`, `.../agent-sdk/observability`, fetched 2026-09-08)

Three independent, separately-enabled signals: **Metrics** (`OTEL_METRICS_EXPORTER=otlp|prometheus|console|none`) — counters for CLI sessions, modified lines of code, PR creations, git commits, session cost in USD, token usage, tool permission decisions, total active time; **Logs** (`OTEL_LOGS_EXPORTER`) — structured records for prompts, API requests, errors, tool results; **Traces** (`OTEL_TRACES_EXPORTER` + `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`) — spans for interactions, model requests, tool calls, and **hooks**. Master switch: `CLAUDE_CODE_ENABLE_TELEMETRY=1`. Endpoint/protocol via `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_PROTOCOL` (`grpc` shown in the example), auth via `OTEL_EXPORTER_OTLP_HEADERS`. `OTEL_RESOURCE_ATTRIBUTES` lets you tag exported metrics with custom key/value pairs (e.g. `team.id=platform`) for per-orchestration or per-role filtering — directly usable to tag metrics by `orch-id`/role without any custom scraping.

### 4.2 Statusline JSON — full field inventory (`code.claude.com/docs/en/statusline`, fetched 2026-09-08)

This is the schema the daemon currently scrapes into `.usage.json`. Confirmed fields (verbatim structure from the docs' own example payload): `cwd`, `session_id`, `session_name`, `prompt_id`, `transcript_path`, `model.{id,display_name}`, `workspace.{current_dir,project_dir,added_dirs,git_worktree,repo}`, `version`, `output_style.name`, `cost.{total_cost_usd,total_duration_ms,total_api_duration_ms,total_lines_added,total_lines_removed}`, `context_window.{total_input_tokens,total_output_tokens,context_window_size,used_percentage,remaining_percentage,current_usage.{input_tokens,output_tokens,cache_creation_input_tokens,cache_read_input_tokens}}`, `exceeds_200k_tokens`, `fast_mode`, `effort.level`, `thinking.enabled`, **`rate_limits.{five_hour,seven_day}.{used_percentage,resets_at}`**, `vim.mode`, `agent.name`, `pr.{number,url,review_state}`, `worktree.{name,path,branch,original_cwd,original_branch}`.

**Yes — `rate_limits` exists and does carry weekly (`seven_day`) usage-limit data**, confirming the product's need for "live verification" was about *whether this Claude Code version exposes it* (§10 in CLAUDE.md) — it does, structurally. But the docs add an important caveat: *"rate_limits is only present for Claude.ai Pro or Max subscribers after the initial API response"* — i.e., it is **absent for API-key-based auth** and absent on the very first statusline render of a session (before any API response has landed). A daemon polling `.usage.json` immediately after spawning a session, or one running on API-key auth rather than a Pro/Max OAuth login, will see no `rate_limits` key and must not treat that as "0% used."

`context_window` and `cost` values can also be `null` "prior to the first API call or immediately following a compact command until the next response" (same source) — another concrete parsing edge case for a schema-tolerant reader.

### 4.3 `total_cost_usd` in the `-p --output-format json` result vs. statusline's `cost.total_cost_usd`

Both exist and are the same underlying figure at different granularities: the JSON result's `total_cost_usd` is for that one invocation/turn; the statusline's `cost.total_cost_usd` is the running session total. Neither is the authoritative source for **org-wide** billing — for that, Anthropic's Admin API (`client.beta.organization`, beta since 2026-08-26 per the bundled `claude-api` skill) exposes usage/cost reports, though per that same skill, "Usage and cost reports... are not in the SDKs — raw HTTP only."

### 4.4 `ccusage` (WebSearch, 2026-09-08, `ccusage.com`, `npmjs.com/package/ccusage`)

A local, offline, no-API-key CLI that parses the **same local JSONL session transcripts** Claude Code already writes under `~/.claude/projects/` — not the statusline — into daily/weekly/monthly/per-session/5-hour-block cost reports with per-model and cache-token breakdowns, using bundled/offline pricing data. It is a reference implementation worth reading for its pricing-multiplier math (it must already implement the exact §3.4 cache-tier weighting correctly to produce accurate numbers) rather than a tool to depend on directly, since AIOrchestrator already has a .NET daemon that could read the same JSONL transcripts natively.

### 4.5 Recommended telemetry design (replacing statusline-scraping)

1. **Primary**: turn on OTel metrics export (`CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_METRICS_EXPORTER=otlp`) pointed at a lightweight local collector (or even `console`/`prometheus` for a single-VPS setup with no existing OTel stack) — this gets cost, token, and tool-decision counters **natively tagged per session via `OTEL_RESOURCE_ATTRIBUTES`**, without any statusline JSON parsing, and without the null/absent-field edge cases in §4.2.
2. **Secondary, for anything OTel doesn't carry (e.g. `rate_limits`)**: keep reading the statusline JSON, but make the reader schema-tolerant per §4.2's documented null/absent cases (the project's own CLAUDE.md decision 21 already mandates schema-tolerant parsing for the usage-limit alerts, so this is confirmation, not new work).
3. **Tertiary, cheap sanity check**: parse `--output-format json`'s `total_cost_usd` per headless turn directly in the daemon's own subprocess-result handling — this is the one number the daemon controls the collection of end-to-end (no polling, no file-watch race), and it's already available from every `-p` invocation the daemon makes.
4. Stop relying on statusline `.usage.json` as the *only* source — it was designed for a human's terminal, not a multi-session daemon; OTel was designed for exactly this shape of consumer.

## 5. Hooks & governance

### 5.1 Hook events — the full available set (`code.claude.com/docs/en/hooks`, `.../agent-sdk/hooks`, fetched 2026-09-08)

Confirmed named events across the two docs pages: `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `UserPromptSubmit`, `SessionStart`, `SessionEnd`, `Setup`, `Stop`, `SubagentStart`, `SubagentStop`, `PreCompact`, `PostCompact`, `PermissionRequest`, `PermissionDenied`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`, `WorktreeCreate`, `Elicitation`, `FileChanged`. This is materially more than the brief's list (which is a reasonable "the important ones" subset) — `PostToolUseFailure`, `PermissionDenied`, `Setup`, `WorktreeCreate`, `Elicitation`, and `FileChanged` are additions worth knowing about specifically because AIOrchestrator's product decisions already care about worktree hygiene (decision 17) and file-for-owner delivery (recent commits: "a file for the owner never vanishes in silence").

**Decision-control varies by event, documented explicitly**: *"Events like TaskCreated, PreToolUse, PermissionRequest, and Elicitation can allow, deny, block, or modify decisions... events like SessionStart and SubagentStart only inject additional context... events such as SessionEnd, Notification, or FileChanged provide no decision control and are used strictly for side effects like logging or cleanup."* This taxonomy matters directly for decision 21 in the project's CLAUDE.md ("hooks ADVISE, the app ENFORCES") — it confirms some hook events are structurally incapable of blocking anything (SessionEnd/Notification/FileChanged), so any governance logic currently attached to those events for enforcement purposes is a no-op by design, not by bug.

### 5.2 `additionalContext` injection and `decision: block` — exact wire shapes (context7, `hooks-guide`/`hooks` pages)

`UserPromptSubmit` example: `additionalContext` **must** be nested under `hookSpecificOutput` — *"Placing additionalContext at the JSON root causes Claude Code to ignore it"* (a documented footgun worth checking AIOrchestrator's own hook scripts against directly). `PreToolUse` decision-control shape: `hookSpecificOutput.{hookEventName, permissionDecision: "allow"|"deny"|..., permissionDecisionReason, updatedInput, additionalContext}` — note `updatedInput` **replaces the entire input object**, not a merge/patch. Exit-code protocol for shell hooks: exit `0` = "no decision; the normal permission flow applies"; exit `2` = block, with **stderr becoming Claude's feedback** (`echo "..." >&2; exit 2`). `PreCompact` hook input carries `trigger: "manual"|"auto"` and `custom_instructions`; can be blocked the same way (exit 2 or a block-decision JSON) to prevent compaction outright.

### 5.3 Sandboxing (`code.claude.com/docs/en/sandboxing`, fetched 2026-09-08)

The sandboxed Bash tool uses **native OS primitives**: **Seatbelt on macOS**, **bubblewrap on Linux and WSL2** (explicitly **not WSL1**, "because bubblewrap relies on kernel features only present in WSL2"). On Ubuntu 24.04+, an AppArmor profile may need to be installed to let bubblewrap create unprivileged user namespaces (a specific `sudo tee /etc/apparmor.d/bwrap` snippet is documented, gated behind checking `sysctl kernel.apparmor_restrict_unprivileged_userns`). **Relevant to the VPS target** (per the project's `.claude/rules/git-and-boundaries.md`, the orchestrator runs on a Linux VPS): this is a genuine, kernel-level sandbox — the correct native replacement for any custom bash-hook logic in AIOrchestrator whose sole job is "stop the agent from doing something destructive to the filesystem/network," as opposed to logic that's actually product-specific policy (channel-file discipline, PLAN.md ledger shape, etc.) which has no native equivalent and must stay a hook/app-enforced check.

### 5.4 Permission modes (source: local `--help` + `agent-sdk/typescript` docs)

CLI `--permission-mode` choices (verbatim from installed help): `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`. The SDK's `PermissionMode` type (TypeScript, `code.claude.com/docs/en/agent-sdk/typescript`) documents each: `"default"` (standard prompts), `"acceptEdits"` (auto-accept file edits), `"bypassPermissions"` (bypass permission checks; "explicit ask rules still prompt" — i.e., bypass is not absolute if a rule explicitly demands confirmation), `"plan"` (read-only exploration), `"dontAsk"` (deny anything not pre-approved, no prompt), `"auto"` (a **model classifier** approves/denies permission prompts — this is the "auto mode" referenced in the user's global CLAUDE.md's "never assume the harness will stop you" prudence rule; note it is a *model's judgment call*, not a deterministic gate, which is exactly why that global rule insists a governing condition "must be visible to the session," resolved by command, never assumed). `--allow-dangerously-skip-permissions` (distinct flag) enables bypass **as an option** without making it the default — for sandboxes only, per its own help text. Org-level lockout: `settings.json`'s `permissions.disableBypassPermissionsMode: "disable"` prevents users from invoking bypass at all, including via subagent definitions (`code.claude.com/docs/en/settings-reference`).

### 5.5 What of AIOrchestrator's custom bash hooks could become native config

See the synthesis table in §6 — the general rule surfaced by this research: **hooks whose job is a hard-coded, universal invariant** (dangerous-command blocking, forbidden paths, secrets-in-diff scanning) map cleanly onto native `PreToolUse` hooks with `exit 2`/`permissionDecision: deny`, or better, onto the OS-level sandbox (§5.3) which enforces the same invariant without relying on the agent's own process staying honest — consistent with decision 21's own reasoning ("every session runs as the same OS user as the app... a hook there restrains an honest session and stops nobody else"). **Hooks whose job is product-specific policy** (PLAN.md ledger shape, channel-header trust, staging discipline) have no native equivalent and must stay custom — Anthropic's hook system gives you the event/decision *mechanism*, not the *policy*.

## 7. Recommended target stack (one-owner, VPS-hosted, phone-driven, 2026)

1. **Transport stays the CLI, shelled out from the .NET daemon** (§1.4) — no official .NET Agent SDK exists; a Node sidecar is only worth the added process boundary if a specific SDK-only capability becomes a hard requirement (in-process MCP tools, `sessionStore`, structured-output retries) rather than "the SDK feels nicer."
2. **Adopt fresh-session-per-turn + digest + STATE block** — directly supported by Anthropic's own context-engineering post (§3.1) and reinforced by context-rot evidence (§3.3: degradation starts well before the window fills, so "resume one huge transcript" is a quality risk, not only a cost one) and by the multi-agent research post's 1,000–2,000-token condensed-summary figure (§3.2) as a concrete target size for what a fresh turn's digest should contain.
3. **Move cost/usage telemetry onto OpenTelemetry** (§4.5) as the primary source, keep statusline JSON only for `rate_limits` (with the documented null/absent-field cases handled), and **re-derive every cost figure through the §3.4 cache-multiplier math** rather than raw token counts — this alone likely closes a real accuracy gap in the existing `.usage.json`-based cost ledger.
4. **Keep the channel-file / hub-and-spoke architecture as-is** — it is not "the thing to migrate off of Agent Teams," it is functionally the right shape for a headless, multi-process, phone-mirrored system, and Agent Teams is architecturally unavailable to a `-p`-driven daemon anyway (§2.1). Optionally pilot **cross-session messaging** (§2.2) for lightweight one-off pings between already-running sessions, but verify headless applicability first — don't assume.
5. **Spike `claude --bg`/`claude agents`/`claude respawn`** (§2.4) against the daemon's actual process-management needs before writing it off or adopting it; this is the one concrete "maybe replace hand-rolled infra with a native command" opportunity this research surfaced that wasn't already in the brief's five questions.
6. **Add a hook-based turn/tool-call counter** to backstop the missing `--max-turns` CLI flag (§1.1, §6), since `--max-budget-usd` alone caps dollars, not runaway iteration count, and a `Stop`/`PreToolUse` hook is the only native way to enforce a hard turn ceiling on this CLI version.
7. **Sandbox the VPS-hosted sessions with bubblergap** (§5.3) as the actual enforcement layer for anything currently relying on a bash hook to "advise" against destructive commands — consistent with the project's own decision 21 that hooks advise and the app (or, natively, the OS sandbox) enforces.
8. **Treat hooks as split into two buckets** (§5.5, §6): generic-safety hooks → candidates for native `PreToolUse`/sandbox replacement; product-policy hooks (PLAN.md shape, channel trust, staging discipline) → no native replacement exists, keep them, and keep them scoped to the daemon-enforced boundary per decision 21 rather than trusting a session's own hook to self-police.
