# Multi-Agent AI Coding Orchestration — Landscape Report (2025–2026)

Compiled 2026-09-08. Scope: tools that orchestrate multiple AI coding agents (Claude Code, Codex, and others) with some form of human supervision, benchmarked against **AIOrchestrator** (private product): one expensive-model SUPERVISOR Claude Code session gates work, N cheaper IMPLEMENTER sessions write code in git worktrees, a REVIEWER role, coordination via append-only markdown channel files tailed by a C#/.NET bridge daemon that mirrors to a Telegram forum supergroup (one topic per orchestration) and routes owner replies back; a PLAN.md ledger per orchestration; sessions run headlessly via `claude -p` (resume or fresh); cost tracked per session; owner mostly on the phone. Known weaknesses: very high token cost (each implementer turn re-reads a ~250k-token transcript), an 87 KB supervisor prompt, fragile regex parsing of LLM-written markdown, and heavy bespoke plumbing.

Every product claim below is cited with a URL and a date. Anything I could not confirm from a source is marked **[unverified]**.

## 1. Anthropic-native tooling

### 1.1 Claude Code Agent Teams
- **What it is**: an experimental in-product feature (env var `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) that lets one Claude Code session (the "team lead") spawn other full Claude Code sessions ("teammates") that work and communicate independently. Source: official docs, current as of Claude Code v2.1.178+, fetched 2026-09-08 — [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams).
- **Topology**: leader + N teammates, but explicitly *not* hierarchical after spawn — "teammates message each other directly," no nesting (teammates cannot spawn their own teammates), one team per session, lead is fixed for the session's life (per the docs above).
- **Communication**: a JSON **mailbox** per agent at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`; messages are validated on read, malformed entries are dropped and logged as errors rather than silently blocking delivery (fixed behavior as of v2.1.207) (same source).
- **Task tracking**: a **shared task list** (not an external tracker) with three states (pending/in-progress/completed) and dependency edges; task claiming uses file locking to avoid races; a teammate self-claims the next unblocked task after finishing one (same source).
- **State/memory model**: each teammate is a fresh Claude Code session — loads CLAUDE.md/MCP/skills fresh, gets the spawn prompt, but does **not** inherit the lead's conversation history. Team config is ephemeral (`~/.claude/teams/{team-name}/config.json`, deleted at session end); the task-list directory persists locally (not uploaded) so a resumed session keeps its tasks, but **in-process teammates themselves do not survive `/resume`** — this is called out explicitly as a current limitation (same source).
- **Human-in-the-loop**: the owner is in the lead's terminal; teammate permission prompts bubble up to the lead's terminal for approval; plan-mode teammates get their plans auto-approved by the lead without a prompt to the human (same source).
- **Cost controls**: none built-in beyond model selection per teammate; the docs are blunt that "agent teams use significantly more tokens than a single session," recommend starting with 3–5 teammates, and note in-process teammates fall outside the main 1-hour prompt-cache bucket by default (5 min TTL unless `subagentPromptCacheTtl` is raised) (same source).
- **Isolation**: no built-in git worktree automation — teammates just work in the same checkout unless the human/lead sets up worktrees manually; the docs' own advice is "avoid file conflicts... break the work so each teammate owns a different set of files" (same source).
- **Maturity**: experimental, disabled by default, shipped ~February 2026 alongside Opus 4.6 per third-party coverage — [alexop.dev, "From Tasks to Swarms," 2026](https://alexop.dev/posts/from-tasks-to-swarms-agent-teams-in-claude-code/). Not open source (built into the closed-source Claude Code CLI).

### 1.2 Claude Code Cross-Session Messaging
- **What it is**: a lighter, non-team feature — independent Claude Code sessions on the same machine (or macOS/Linux/WSL2, native Windows from v2.1.234) discover each other via a new `ListAgents` tool and exchange plain-text messages via `SendMessage`, shipped v2.1.224, August 2026 — [code.claude.com/docs/en/cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging); corroborated by [9to5Mac, 2026-08-07](https://9to5mac.com/2026/08/07/claude-code-now-lets-sessions-talk-to-each-other-on-macos/) and [MacRumors, 2026-08-08](https://www.macrumors.com/2026/08/08/claude-code-adds-cross-session-messaging/).
- **Key property**: only text passes — no conversation history, files, or permissions — and delivery goes over a **per-session local socket on the machine, never through Anthropic's servers** (same docs). This is architecturally close to what AIOrchestrator's channel files do, but Anthropic's version needs no shared filesystem markdown file and no external transport.

### 1.3 Claude Code Sub-agents (Agent tool / `.claude/agents`)
- **What it is**: the older, simpler delegation primitive — a parent session calls the `Agent` tool (renamed from `Task` in v2.1.63) with a `subagent_type`; the subagent runs in its own context window with a custom system prompt and a restricted tool list, then returns one final result to the caller. Definitions live as markdown files in `.claude/agents/` (project) or `~/.claude/agents/` (user) — [code.claude.com/docs/en/sub-agents](https://code.claude.com/docs/en/sub-agents), via search summary dated 2026.
- **vs Agent Teams**: subagents report back to the parent only (no peer messaging, no shared task list, cheaper — result is summarized back into the caller's context rather than each agent burning its own full context) — this contrast is spelled out explicitly in Anthropic's own comparison table in the Agent Teams doc (§1.1 source).
- **Relevant to AIOrchestrator**: this is functionally the closest Anthropic-native analogue to the SUPERVISOR→IMPLEMENTER dispatch, except it is synchronous/blocking within one process rather than N independently-running headless CLI processes coordinated over files.

### 1.4 Claude Code on the web / Remote Control
- **Claude Code on the web**: sessions run entirely on Anthropic-managed cloud infrastructure (fresh sandbox, no local toolchain access) — search summary, 2026, corroborated by [clauderemotecontrol.com comparison page, 2026](https://clauderemotecontrol.com/claude-code-on-the-web/).
- **Remote Control**: a *different*, newer feature (research preview, ~February 2026) that is NOT cloud compute — it's a sync/bridge layer connecting a **local** terminal session to the claude.ai web UI and the iOS/Android apps; only chat + tool results cross the encrypted bridge, files/MCP/env stay local — [Simon Willison, 2026-02-25](https://simonwillison.net/2026/Feb/25/claude-code-remote-control/); [DataCamp guide, 2026](https://www.datacamp.com/tutorial/claude-code-remote-control).
- **Relevance to AIOrchestrator**: this is the first-party version of exactly what AIOrchestrator's Telegram bridge does for the owner (phone as a window into a session that keeps running locally) — except scoped to Anthropic's own mobile/web clients rather than Telegram, and 1:1 session↔phone rather than N sessions mirrored into one forum.

### 1.5 Claude Agent SDK
- **What it is**: the SDK version of the Claude Code harness for building custom agents; `query()` takes `continue`/`resume`/`fork` options — continue/resume both extend an existing session, fork copies history into a *new* session while leaving the original untouched — [platform.claude.com/docs/en/agent-sdk/sessions](https://platform.claude.com/docs/en/agent-sdk/sessions), search summary 2026.
- **Hooks**: lifecycle callbacks — `pre_tool_use`, `post_tool_use`, `post_tool_use_failure`, `user_prompt_submit`, `stop`, `subagent_start`, `subagent_stop`, `pre_compact`, `notification`, `permission_request`, `session_start`, `session_end`, `message_display` — [platform.claude.com/docs/en/agent-sdk/hooks](https://platform.claude.com/docs/en/agent-sdk/hooks).
- **Permission callbacks**: `ClaudeAgentOptions` carries a callback for tool-permission checks, independent of hooks.
- **Relevance**: AIOrchestrator's `claude -p` headless-turn model with resume/fresh is a hand-rolled version of exactly this SDK primitive; the SDK's `fork` (copy history into a new session, keep original intact) is a capability AIOrchestrator does not currently use but that maps directly onto "branch an implementer's context to try an alternative without losing the original."

### 1.6 Claude Managed Agents
- **What it is**: a suite of composable, Anthropic-hosted APIs for cloud agents — sandboxed execution, checkpointing, credential management, scoped permissions, end-to-end tracing — announced 2026-04-08 — [claude.com/blog/claude-managed-agents](https://claude.com/blog/claude-managed-agents); [InfoWorld, 2026-04-08](https://www.infoworld.com/article/4156852/anthropic-rolls-out-claude-managed-agents.html).
- **Pricing**: standard token rates + **$0.08/session-hour** for active runtime, no flat fee (same sources).
- **Status**: multi-agent coordination and self-evaluation are still "research preview," gated behind separate access requests (same sources). Not directly comparable to AIOrchestrator (this is an API product for *building* hosted agents, not an orchestration UI), but it validates the "pay per session-hour, not per token alone" cost model as an industry direction.

### 1.7 Claude Code scheduled tasks / Routines
- **What it is**: three tiers of "run without a human present" — session-scoped loops (need an open session), Desktop scheduled tasks (need the machine on), and cloud **Routines** (need neither, run on Anthropic's cloud, cron-style presets + API/GitHub-event triggers) — shipped April 2026, research preview — [The Register, 2026-04-14](https://www.theregister.com/2026/04/14/claude_code_routines/); [MakerKit guide, 2026](https://makerkit.dev/blog/tutorials/claude-code-routines-guide).
- **Distinction from cron**: "a Claude routine runs an agent that reasons about context... and proposes a fix as a pull request" rather than running fixed steps (same sources).

### 1.8 Claude Code "channels" (Telegram/Discord plugin) — verified but currently unstable
- **What it is**: confirmed to exist. A "channel" is an MCP server Claude Code spawns as a local subprocess over stdio; it lets Telegram/Discord/iMessage act as the chat interface for a *single* Claude Code session — search summary, 2026, corroborated by GitHub issues.
- **Caveat — reliability**: multiple open GitHub issues from 2026 report the official Telegram channel plugin's inbound-message delivery is broken: notifications are sent but never surface as `<channel>` tags in the conversation, i.e., outbound (Claude → phone) works but inbound (phone → Claude) frequently does not — [anthropics/claude-code#36802](https://github.com/anthropics/claude-code/issues/36802), [#38110](https://github.com/anthropics/claude-code/issues/38110), [#36472](https://github.com/anthropics/claude-code/issues/36472), [#37498](https://github.com/anthropics/claude-code/issues/37498), all filed 2026.
- **Relevance to AIOrchestrator**: this is the single most direct first-party competitor to AIOrchestrator's whole raison d'être (Telegram-mirrored supervision) — and it is *single-session*, not multi-orchestration/multi-topic, and per public bug reports is presently less reliable inbound than AIOrchestrator's own bridge. Worth monitoring for whether Anthropic fixes and extends this into something that obsoletes part of AIOrchestrator's bridge.

### 1.9 Hooks + OpenTelemetry
- **What it is**: `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus standard `OTEL_*` env vars export three signals — metrics (sessions, token usage, cost), log events, and traces (traces in beta as of v2.1.121) — over OTLP to any compatible backend (Grafana, Datadog, Honeycomb, SigNoz) — [code.claude.com/docs/en/monitoring-usage](https://code.claude.com/docs/en/monitoring-usage); [SigNoz blog, 2026](https://signoz.io/blog/claude-code-monitoring-with-opentelemetry/); [Dash0 guide, 2026](https://www.dash0.com/guides/monitoring-claude-code-opentelemetry). Third-party wrapper example: `claudia` (drop-in replacement for the `claude` command that logs to Logfire/Sentry/Honeycomb/Datadog) — [github.com/TechNickAI/claude_telemetry](https://github.com/TechNickAI/claude_telemetry).
- **Relevance**: AIOrchestrator's bespoke `statusline.ps1`-as-probe + `UsageTotals_Reader` accumulator duplicates what OTel export already gives for free in a standard, tool-agnostic format (Grafana dashboards, alerting) instead of a custom C# reader with its own bug class (per-session double counting, the kind decision 10 in AIOrchestrator's CLAUDE.md already had to fix once).

## 2. OpenAI ecosystem

### 2.1 Codex CLI / cloud
- Open-sourced April 16, 2025, terminal-native agent — [Wikipedia, "OpenAI Codex (AI agent)"](https://en.wikipedia.org/wiki/OpenAI_Codex_(AI_agent)), search summary 2026.
- **Cloud delegation**: `codex cloud exec` — describe a task, Codex spins up a cloud environment, runs the agent, returns a diff — [Blake Crosley, "Codex CLI Guide 2026"](https://blakecrosley.com/guides/codex).
- **Multi-agent**: stabilized as opt-in in Codex CLI v0.145.0 (2026-07-21), with configurable sub-agent models, reasoning levels, and concurrency — search summary, corroborated by [IntuitionLabs, "OpenAI Codex App"](https://intuitionlabs.ai/articles/openai-codex-app-ai-coding-agents).
- **Direction**: "Codex Jobs" running entirely in OpenAI's cloud on triggers — pointing toward the same "SaaS devops tool" shape as Claude Code Routines (same sources).

### 2.2 OpenAI Symphony — issue-tracker-as-control-plane (the single most relevant find)
- **What it is**: an **open-source (Apache 2.0), Elixir/OTP-built** orchestrator, released 2026-04-27, that maps **every open Linear issue to a dedicated Codex agent workspace** and keeps polling — [openai.com/index/open-source-codex-orchestration-symphony](https://openai.com/index/open-source-codex-orchestration-symphony/); [Help Net Security, 2026-04-28](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/).
- **Mechanics**: polls Linear every 30 seconds, creates an **isolated sandbox per issue**, dispatches an agent, and keeps it running until the issue is done — **no human supervision required by default** — [MindStudio summary, 2026](https://www.mindstudio.ai/blog/openai-symphony-spec-linear-agent-control-plane-500-percent-pr-increase).
- **Reported impact**: OpenAI's internal teams saw a **500% increase in landed PRs** using Symphony (same source; also [Help Net Security](https://www.helpnetsecurity.com/2026/04/28/openai-symphony-codex-orchestration-linear/)).
- **Architecture choice**: BEAM/OTP specifically for fault tolerance and lightweight concurrency to run "dozens of coding agents in parallel on a single node" — this is a direct, considered rebuttal of the idea that you need heavyweight orchestration infra; a persistent supervised process tree with cheap concurrent processes, not a UI app spawning OS processes.
- **v1.1.0 update**: added support for the Kata CLI (based on `pi-coding-agent`) as an alternative agent runtime — opening the door to running Claude Code, Gemini, etc. inside the same orchestration framework, i.e., Symphony is moving toward being **agent-agnostic**, exactly like AIOrchestrator's own multi-agent ambition, but built around an issue tracker rather than a bespoke ledger — [GitHub issue tracker summary via search, 2026].
- **Governance/gating**: the model is explicitly ticket-driven and largely autonomous, the opposite end of the spectrum from AIOrchestrator's supervisor-gates-everything design — worth flagging as a real industry data point that heavy human gating is *not* the only successful shape, at least for OpenAI's own internal workflow.

### 2.3 Codex browser extension / app multi-agent — **[unverified]**
- A Chrome extension launched May 2026, with other browsers added August 25, 2026, per search summary (IntuitionLabs / blakecrosley.com articles) — I was not able to independently verify a primary OpenAI source for this within the scope of this research; treat as **[unverified]**.

## 3. Third-party orchestrators and managers

### 3.1 Conductor (conductor.build)
- macOS app by Melty Labs; orchestrates parallel Claude Code and Codex agents, each in an isolated git worktree; free, bring-your-own-subscription — [CodePick guide, 2026](https://codepick.dev/en/guides/conductor-build-intro/); [Developers Digest review, 2026](https://www.developersdigest.tech/tools/conductor).
- Positioning: "local-orchestrator layer" — dispatch, isolation, diff-first review UI; agents do the coding, Conductor does workspace/branch management (same sources). Best fit cited as 3–10 agents on known codebases — [Nimbalyst, "Best Multi-Agent Coding Tools 2026"](https://nimbalyst.com/blog/best-multi-agent-coding-tools-2026/).
- Not open source [unverified — no explicit license statement found in sources]. Mac-only.

### 3.2 claude-squad
- Open source (GitHub, `smtg-ai/claude-squad`); manages multiple terminal agents (Claude Code, Codex, OpenCode, Amp) using **tmux** for session multiplexing and **git worktrees** for isolation, single TUI for review/navigation — [smtg-ai.github.io/claude-squad](https://smtg-ai.github.io/claude-squad/); [GitHub repo](https://github.com/smtg-ai/claude-squad).

### 3.3 ccmanager
- Open source (`kbwo/ccmanager`); session manager across a wider set of CLIs (Claude Code, Gemini CLI, Codex CLI, Cursor Agent, Copilot CLI, Cline CLI, OpenCode, Kimi CLI); deliberately avoids tmux, shows live per-session state (busy/waiting/idle) — [github.com/kbwo/ccmanager](https://github.com/kbwo/ccmanager); [x-cmd install guide, 2026](https://www.x-cmd.com/install/ccmanager/).
- **Relevance**: the busy/waiting/idle live state view is close to AIOrchestrator's per-member state chips (implementer working / awaiting review / writing window open / blocked on owner) — validates that pattern as converged-upon, but ccmanager derives it without needing markdown-channel parsing.

### 3.4 Vibe Kanban
- Open source, web-based kanban orchestration layer for local coding agents (Claude Code, Gemini CLI, Codex, Amp, others via MCP) — 26.4k GitHub stars, 30k+ users cited — [vibekanban.com](https://vibekanban.com/); [Isomoes blog, 2026](https://isomoes.github.io/en/blog/tools/vibe-kanban-intro/).
- Every task = its own git worktree; runs dev servers per task; supports commenting on AI-generated code for QA — [oss-ai-swe.org](https://oss-ai-swe.org/vibe-kanban/).
- **Business status**: Bloop (the company behind it) shut down 2026-04-10; project continues community-maintained, cloud features removed, fully local now — [search summary, 2026, citing Bloop shutdown announcement]. Demonstrates the risk of VC-funded orchestration layers around a still-free underlying model — relevant since AIOrchestrator is self-hosted and doesn't carry that risk.

### 3.5 Ruflo (formerly Claude Flow)
- Open source (`ruvnet/ruflo`), renamed from "Claude Flow" in January 2026 to avoid trademark conflict (npm package/CLI still called `claude-flow`) — [GitHub repo](https://github.com/ruvnet/ruflo); [DEV Community history piece, 2026](https://dev.to/stevengonsalvez/claude-flow-the-multi-agent-swarm-orchestrator-before-it-got-a-new-name-4kd4).
- **Architecture**: "hive-mind" system — a hierarchy of "queen" (decision) agents and "worker" (executor) agents, shared memory, consensus mechanisms, claimed 54+ specialized agent types — same sources.
- **Claimed results**: v3 reportedly scores 84.8% on SWE-Bench; 40,800+ GitHub stars cited — [Tosea.ai guide, 2026](https://tosea.ai/blog/ruflo-enterprise-ai-multi-agent-guide-2026) — **[unverified benchmark number, taken from third-party marketing coverage rather than the SWE-Bench leaderboard directly]**.

### 3.6 Gas Town (Steve Yegge)
- Go-based, tmux-driven orchestrator for **20–30 parallel agents**, released ~early January 2026 by Steve Yegge, built on his "Beads" framework — [ASCII News, 2026-01-02](https://ascii.co.uk/news/article/news-20260102-190a5f9f/steve-yegge-releases-gas-town-multi-agent-orchestrator-for-c); [Steve Yegge, Medium, "Welcome to Gas Town"](https://steve-yegge.medium.com/welcome-to-gas-town-4f25ee16dd04).
- **Seven named agent roles**: Mayor, Polecats, Refinery, Witness, Deacon, Dogs, Crew — handling coding, testing, orchestration, review, and ops maintenance across multiple "rigs" (projects), with merge-queue management and "work swarming" — [The New Stack, on Gas Town going to the cloud](https://thenewstack.io/steve-yegges-ai-agent-orchestration-project-gas-town-comes-to-the-cloud-and-brings-the-wasteland-with-it/).
- **Explicit target audience**: Yegge's own material gates this at "Stage 6/7" agentic-coding maturity — not aimed at casual users (same New Stack source, and Yegge's own posts).
- **Relevance**: closest philosophical peer to AIOrchestrator in scale ambition and role specialization (Mayor≈Supervisor, Witness≈Reviewer), but built for a much larger swarm (20-30 vs AIOrchestrator's typical few-implementer topology) and using durable role names/merge-queue discipline instead of markdown channel files.

### 3.7 Paperclip (paperclip.ing)
- Open source (MIT, Node.js + React), self-hosted **control plane, not an agent itself** — org chart, budgets, ticketing, human approvals for a swarm of agents; bring-your-own-agent (OpenClaw, Claude Code, Codex, Cursor, OpenRouter) — [paperclip.ing](https://paperclip.ing/); [github.com/agencyenterprise/paperclip-ai](https://github.com/agencyenterprise/paperclip-ai).
- **Execution model**: "heartbeats" — agents run in short scheduled work sessions rather than continuously; task checkout and budget enforcement are atomic ("no double-work and no runaway spend") — [Towards AI overview, 2026](https://pub.towardsai.net/paperclip-the-open-source-operating-system-for-zero-human-companies-2c16f3f22182); [UC Strategies, 2026](https://ucstrategies.com/news/paperclip-the-open-source-ai-manager-that-coordinates-multiple-ai-agents/).
- Launched 2026-03-04 by pseudonymous developer @dotta; crossed 30,000 GitHub stars within three weeks (same source) — **[unverified — rapid star counts on GitHub are a weak maturity signal on their own]**.
- **Relevance**: the closest analogue to AIOrchestrator's own ambition to be a generic multi-agent control plane rather than a single coding tool — but Paperclip's "heartbeat" execution and atomic budget/task-checkout primitives are things AIOrchestrator's file-based ledger does not have.

### 3.8 CodeMachine

### 3.11 Factory (Droids)
- "Missions" = structured multi-agent workflows: a coordinator agent decomposes work into milestones and dispatches to specialized droids (code, review, docs, test, "Knowledge") with explicit role boundaries; "Mission Control" is the tracking/intervention UI — [Ry Walker research note, 2026](https://rywalker.com/research/factory-ai); [Developers Digest, "Factory Droid Review," 2026](https://www.developersdigest.tech/blog/factory-droid-review-setup-2026).
- Raised $150M Series C at $1.5B valuation, April 2026; enterprise customers cited include Nvidia, Adobe, Bayer, EY, MongoDB, Zapier — [Idlen news item, 2026-04](https://www.idlen.io/news/factory-ai-150-million-1-5-billion-droids-coding-agents-enterprise-april-2026/).
- **Relevance**: role specialization (code/review/docs/test/knowledge) with an explicit "coordinator decomposes → dispatches" step maps closely onto AIOrchestrator's supervisor/implementer/reviewer split, at enterprise scale and with VC backing.

### 3.12 Google Jules
- Async-by-design: submit a GitHub issue/task, Jules opens an isolated Google-managed cloud VM, plans, implements, runs tests, opens a PR — no live chat loop — [search summary, 2026]; corroborated by [Digital Applied, "Google Jules Guide 2026"](https://www.digitalapplied.com/blog/google-jules-gemini-async-coding-agent-guide).
- **Explicit non-goal**: "Each Jules task is independent. Tasks cannot communicate with each other, share context, or coordinate on related changes. No multi-agent orchestration" (same source) — an important negative data point: not every serious player believes cross-agent coordination is necessary; queue-of-independent-tasks is a deliberate design choice, not an oversight.
- 2026 update: closes the CI loop — a failing PR check is read by Jules automatically, fixed, and re-pushed without developer intervention (same source).

### 3.13 GitHub Copilot coding agent
- New standalone "GitHub Copilot app" (announced Microsoft Build 2026) as a control center for multiple parallel agents across repos — [DevOps.com, 2026](https://devops.com/github-copilot-gets-its-own-app-and-agents-are-the-reason-why/).
- `/fleet` slash command in Copilot CLI: an orchestrator plans and splits an objective into independent work items and dispatches multiple subagents concurrently — [GitHub Blog, 2026](https://github.blog/ai-and-ml/github-copilot/run-multiple-agents-at-once-with-fleet-in-copilot-cli/).
- Custom agents + sub-agent orchestration: developers define scoped agents (tools + prompt); the Copilot runtime auto-delegates to the right one as an isolated sub-agent, streaming lifecycle events back to the parent — [GitHub Docs, "Custom agents and sub-agent orchestration"](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/custom-agents).
- Every agent session runs in its own isolated git worktree, so parallel agents don't collide (same GitHub Blog source). Also supports running Claude and Codex agents alongside native Copilot agents in the same app (same source).

### 3.14 Amp (Sourcegraph)

## 5. Synthesis

### (a) Patterns converging across the industry

1. **Git worktree (or ephemeral cloud sandbox) per unit of work is now nearly universal.** Every serious tool surveyed — Agent Teams (manually, per docs' own advice), Conductor, claude-squad, ccmanager, Vibe Kanban, Cursor background agents, GitHub Copilot coding agent, Symphony, Factory Missions — isolates each concurrent agent's edits in its own workspace before merge. AIOrchestrator already does this (worktrees for implementers).
2. **The issue/task tracker (or a task-list primitive standing in for one) is becoming the coordination substrate**, not chat transcripts. Symphony explicitly treats Linear as "the control plane"; Agent Teams' shared task list with dependency edges is Anthropic's own in-process version of the same idea; Vibe Kanban and Factory's Mission Control are UI-native kanban boards. The direction is: state lives in a structured, queryable store (tracker/DB/task-list with typed states and dependencies), not in free-form prose a parser has to regex.
3. **PR (or an equivalent named diff) is the universal unit of human review**, whether the reviewer is a human or another agent. Symphony, Jules, Cursor, GitHub Copilot, Cognition's Fusion, and Amp's subagents all converge on "agent produces a diff/PR, review happens there," rather than reviewing a live transcript.
4. **Ephemeral, cloud-hosted execution is displacing "must keep your laptop open."** Jules, Cursor background agents, Codex Cloud, Ona (OpenAI's acquisition specifically to solve this), and Claude Code Routines all treat "survives your laptop closing" as a first-class requirement, not a nice-to-have. This is the most consequential structural gap for a locally-spawned-terminal architecture like AIOrchestrator's.
5. **Structured message/mailbox protocols, not shared prose files, are the emerging inter-agent transport.** Agent Teams' per-agent JSON mailbox with schema validation (malformed entries are dropped + logged, not silently corrupting state) is a direct, load-bearing counter-example to AIOrchestrator's markdown-channel-plus-regex approach, and it comes from the same vendor whose CLI AIOrchestrator wraps.
6. **Web/mobile control surfaces for the human are now standard, and increasingly first-party.** Remote Control, Claude Code on the web, Cursor 3's Agents Window, Devin's Agent Command Center, Factory's Mission Control, and the entire Omnara/Happy/OpenClaw/claude-code-telegram cluster all put a phone or a hosted web UI between the human and N running agents.
7. **Multiple, independent projects have converged on Telegram (specifically forum topics) as the messaging surface of choice for this exact problem** — OpenClaw's topic routing and at least five separate open-source `claude-code-telegram` projects. This validates, rather than undermines, AIOrchestrator's specific transport choice — it is a heavily-trodden path, not an idiosyncratic one.
8. **A live per-agent state indicator (busy/waiting/idle, or richer) is table stakes**, seen in ccmanager, Agent Teams' agent panel, Factory Mission Control, Devin's Agent Command Center. AIOrchestrator's per-member state chips are directionally correct but are derived by parsing markdown rather than reading a typed state machine.
9. **Autonomy-without-gating is a real, not fringe, choice** at the frontier — Symphony explicitly runs "no human supervision required," and Jules deliberately has *no* cross-task coordination at all, treating that as a feature. This tempers, but does not refute, AIOrchestrator's supervisor-gates-everything model: gating is one legitimate point on a spectrum, not the only sane design, and the heaviest-gated products in this survey (AIOrchestrator among them) are not the ones citing the largest productivity numbers (Symphony's 500% figure came specifically from removing a human gate, not adding one).
10. **Orchestration-as-a-dedicated-mode is being questioned even by tools that pioneered it** — Kilo Code retired its dedicated "Orchestrator" mode in 2026 because ordinary delegation from any mode became good enough. This is a useful data point against reflexively adding more bespoke orchestration surface area.

### (b) Where AIOrchestrator is unusual, and what the evidence says

| AIOrchestrator choice | How unusual | What the evidence suggests |
|---|---|---|
| **Markdown channel files, regex-parsed** | Unusual among the vendor/venture-funded tools (all use JSON/DB/tracker state); *not* unusual among hobbyist open-source Telegram bridges, which tend to be similarly ad hoc. | Likely **worse** than the emerging norm specifically because of the regex-fragility already logged in AIOrchestrator's own CLAUDE.md (decision 12: duplicate `[n]` and stamps; decision 13: non-monotonic counts after compaction). Anthropic's own Agent Teams mailbox is the same *conceptual* idea (append-only, file-based, per-agent) but schema-validated JSON with drop-and-log on malformed entries — a strictly safer version of the same pattern, achievable without discarding the file-based approach entirely. |
| **Telegram, one topic per orchestration** | Not unusual — independently reinvented by OpenClaw and at least five other open-source projects, and is architecturally close to what Anthropic's own (currently buggy) Telegram channel plugin is trying to be. | **Validated, not risky.** This is a heavily-converged-upon shape. The risk is Anthropic's own official channel plugin or Remote Control eventually subsuming this at the platform level — worth tracking, not blocking on. |
| **A C#/.NET desktop app as the bridge daemon** | Very unusual — every comparable tool in this survey (Symphony/Elixir, Vibe Kanban/web, Conductor/Mac-native-presumably-Swift-or-Electron, claude-squad/Go, ccmanager/Node, OpenHands/Python) is either a web app, a CLI, or built in a language chosen for concurrency (Elixir) or cross-platform terminal UI (Go/Rust/Node). | **Just different**, not obviously worse — it matches Nathan's own stated stack preference (WPF/.NET) and the "keep it simple" 2026-08-06 decision already recorded in AIOrchestrator's own CLAUDE.md. But Symphony's explicit architectural bet on Elixir/OTP specifically *for* "dozens of agents in parallel, fault-tolerant" is worth reading as a considered counterpoint if AIOrchestrator ever needs to scale past a handful of implementers — a desktop UI thread and PID-watchdog model doesn't obviously get you the same fault-isolation for free. |
| **Long-lived, resumed headless `claude -p` sessions, each implementer re-reading a ~250k-token transcript per turn** | Unusual and expensive. Every other surveyed tool that runs many agents either (a) spawns a **fresh, short-lived agent per task** (Symphony: dedicated workspace per Linear issue, torn down when done; Jules: one VM per task) or (b) keeps agents alive but relies on **structured state** (task list, mailbox) rather than re-reading a full prose transcript to reconstruct context. | Likely **worse** on the specific, already-diagnosed cost axis. This is the strongest, most actionable finding of this whole survey (see idea list below) — nothing else surveyed re-derives full context from a 250k-token markdown replay on every turn; the norm is either statelessness-by-design (fresh sandbox per task) or a compact structured state object. |
| **Supervisor-as-phone-line: the owner interacts only through the supervisor, at high level** | Somewhat unusual in degree, not in kind. Devin's Command Center, Factory's Mission Control, and Cursor's Agents Window all also present a single pane of glass over N agents — but they are typically **read/steer UIs over agent state**, not a full LLM session mediating every owner interaction. Symphony and Jules go further the other way (no chat mediation at all — the tracker/PR *is* the interface). | **Genuinely a design bet, not obviously right or wrong.** The upside (a reasoning layer between the owner and raw agent noise, matching the proven 1:1 supervisor/implementer pattern this repo generalizes) is real and is exactly the thing Symphony sacrifices for its 500% number. The downside — an always-on expensive-model session as a mandatory relay — has no clean analogue anywhere else in this survey; nobody else pays full inference cost for a permanent phone-line LLM. This is worth an explicit, deliberate check against a cheaper "structured status + occasional narration" alternative, rather than assuming the current shape is load-bearing. |
| **A bespoke PLAN.md ledger instead of an issue tracker** | Unusual relative to the newest frontier tools (Symphony/Linear, Factory/Missions, Vibe Kanban/kanban board), ordinary relative to older/simpler tools. | The clearest, lowest-risk adoption opportunity in this whole report (see idea list) — Symphony's 500% number is attributed specifically to using a *real, typed, dependency-aware* tracker as the control plane, a property free/cheap issue trackers (Linear free tier, GitHub Issues, a local SQLite-backed board) already have and PLAN.md does not. |

### (c) Concrete ideas AIOrchestrator could adopt, each tied to a source

1. **Replace (or supplement) markdown-channel parsing with schema-validated JSON mailboxes, drop-and-log malformed entries instead of failing/misreading them.** Directly modeled on Claude Code Agent Teams' per-agent inbox file and its explicit fix history (a single bad entry used to block delivery every second until manually deleted; now malformed entries are validated out and logged, valid ones still delivered). Source: [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams), §"Architecture."
2. **Give each implementer turn a compact, typed state object instead of a full transcript replay** — a task's current status, dependency list, and last N structured events — rather than re-reading ~250k tokens of prose per turn. Modeled on Agent Teams' shared task list (typed pending/in-progress/completed states, dependency edges, self-claim) and on Symphony's per-issue dedicated (and torn-down) workspace. Sources: [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams); [openai.com/index/open-source-codex-orchestration-symphony](https://openai.com/index/open-source-codex-orchestration-symphony/).
3. **Adopt OpenTelemetry export for usage/cost instead of the bespoke `statusline.ps1`-probe + custom accumulator.** Claude Code already emits metrics/logs/traces over OTLP for exactly this (sessions, tokens, cost, per-model/per-subagent breakdown); wiring the existing bridge to consume that instead of re-deriving totals removes a whole bug class (the double-counting AIOrchestrator's own CLAUDE.md decision 10 had to fix once already) and gets free Grafana/Datadog dashboards. Source: [code.claude.com/docs/en/monitoring-usage](https://code.claude.com/docs/en/monitoring-usage); [SigNoz, 2026](https://signoz.io/blog/claude-code-monitoring-with-opentelemetry/).
4. **Use `fork` (Agent SDK session option) to branch an implementer's context for a risky/alternative approach without losing or duplicating the original transcript**, instead of re-running full turns or hand-managing branches. Source: [platform.claude.com/docs/en/agent-sdk/sessions](https://platform.claude.com/docs/en/agent-sdk/sessions).
5. **Consider a real, lightweight task tracker (even a local one) as the ledger instead of PLAN.md's regex-parsed markdown**, giving typed status + dependency edges "for free" and enabling automatic unblocking, exactly as Agent Teams and Symphony both do. This is the specific mechanism Symphony's operators credit for the 500% PR increase. Source: [openai.com/index/open-source-codex-orchestration-symphony](https://openai.com/index/open-source-codex-orchestration-symphony/); [MindStudio summary, 2026](https://www.mindstudio.ai/blog/openai-symphony-spec-linear-agent-control-plane-500-percent-pr-increase).
6. **Add a cloud/headless fallback so an orchestration survives the owner's machine going to sleep**, at least for long implementer turns — the single most consequential structural gap identified against Jules, Cursor background agents, Claude Code Routines, and OpenAI's Ona acquisition, all of which treat "keeps running after you close the laptop" as core. Sources: [Forbes, 2026-06-13](https://www.forbes.com/sites/janakirammsv/2026/06/13/openai-buys-ona-to-run-codex-agents-inside-enterprise-clouds/); [The Register on Routines, 2026-04-14](https://www.theregister.com/2026/04/14/claude_code_routines/).
7. **Borrow the "hooks enforce quality gates on task lifecycle events" pattern** (`TeammateIdle`, `TaskCreated`, `TaskCompleted` hooks that can block-and-explain, exit code 2 = reject with feedback) as a cleaner mechanism than markdown-channel conventions for the supervisor to gate implementer/reviewer transitions. Source: [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams), §"Enforce quality gates with hooks."
8. **Evaluate Claude Code's own cross-session messaging (`ListAgents`/`SendMessage`, local socket, text-only, no history/files/permissions crossing) as a possible replacement for parts of the file-tailing bridge on machines where all sessions run locally** — it is a first-party, lower-latency, no-parsing alternative for at least the same-machine case. Sources: [code.claude.com/docs/en/cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging); [9to5Mac, 2026-08-07](https://9to5mac.com/2026/08/07/claude-code-now-lets-sessions-talk-to-each-other-on-macos/).
9. **Track Anthropic's own Telegram channel plugin as a potential future replacement for the whole bridge**, but don't rely on it yet — public GitHub issues from 2026 show the inbound-message path (phone → Claude) is still broken in the first-party plugin, while outbound works. Re-evaluate periodically rather than assuming AIOrchestrator's bespoke bridge stays necessary forever. Sources: [anthropics/claude-code#36802](https://github.com/anthropics/claude-code/issues/36802), [#38110](https://github.com/anthropics/claude-code/issues/38110).
10. **Adopt a live, typed per-agent status view (busy/waiting/idle at minimum) sourced from structured events, not markdown parsing** — modeled on ccmanager's explicit non-tmux status display and Agent Teams' own agent panel (idle/working rows, collapsing when many are idle). Sources: [github.com/kbwo/ccmanager](https://github.com/kbwo/ccmanager); [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams).
11. **Reconsider whether the Supervisor must be a full, always-on expensive-model relay for every owner interaction, or whether a cheaper "structured status digest + narration only on request" layer (as Factory's Mission Control and Devin's Command Center do) could cover most phone check-ins**, reserving the expensive supervisor turn for actual gating decisions. No other surveyed product pays full inference cost for a standing phone-line LLM; this is worth a deliberate cost/benefit re-check rather than an assumption. Sources: [rywalker.com/research/factory-ai](https://rywalker.com/research/factory-ai); [Fixed Labs, Devin Desktop review, 2026](https://www.fixedlabs.ai/blog/devin-desktop-review).
12. **If AIOrchestrator ever needs to go beyond a handful of implementers, budget for a concurrency-oriented backend, not just a bigger desktop app** — Symphony's deliberate choice of Elixir/OTP specifically to run "dozens of agents in parallel, fault-tolerant, on a single node" is a considered engineering signal that a UI-thread-plus-PID-watchdog model (AIOrchestrator's current approach) may not scale gracefully past current implementer counts without a redesign. Source: [openai.com/index/open-source-codex-orchestration-symphony](https://openai.com/index/open-source-codex-orchestration-symphony/).
