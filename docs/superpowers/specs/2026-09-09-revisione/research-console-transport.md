# AIOrchestrator research: owner console (phone) and agent transport/state — 2025–2026 landscape

Date of research: 2026-09-08. All claims are cited URL + date where a date was recoverable from the source; items I could not independently confirm are marked **[unverified]**. Figures without a fresh live check are marked **[documented]** (taken from vendor docs/press, not measured by me).

## QUESTION 1 — The owner console on the phone

### 1.1 What Anthropic itself ships today

Anthropic has converged on **three distinct mobile surfaces**, all reached from one Claude app (iOS/Android), documented as of the 2026-09 docs snapshot:

- **Cloud sessions ("Claude Code on the web")** — task runs on Anthropic-managed cloud infrastructure; continues after you close the phone; you start it from claude.ai/code/new or the app's Code tab. ([code.claude.com/docs/en/mobile](https://code.claude.com/docs/en/mobile), fetched 2026-09-08)
- **Remote Control** — connects the phone app to a Claude Code session running on *your own machine*; code execution and filesystem access stay local, the phone is just a window. Shipped **2026-02-24** as a research preview, Max-plan users first. ([Help Net Security, 2026-02-25](https://www.helpnetsecurity.com/2026/02/25/anthropic-remote-control-claude-code-feature/); [TechRadar](https://www.techradar.com/pro/anthropic-reveals-remote-control-a-mobile-version-of-claude-code-to-keep-you-productive-on-the-move)). Architecturally: outbound-HTTPS only, no inbound ports, short-lived scoped credentials, traffic relayed through Anthropic's API — same trust model AIOrchestrator's Telegram bridge uses (mirror, never a listening port). One remote session per Claude Code instance; the local terminal must stay open. Push notifications fire "when a long-running task finishes or needs a decision," or on request ("notify me when tests finish"). Permission modes reachable from mobile are capped: **no Bypass, no Auto for Remote Control** — Manual/Accept-edits/Plan only ([code.claude.com/docs/en/mobile](https://code.claude.com/docs/en/mobile)).
- **Dispatch** — you message a task to the Desktop app and it decides how to run it; Pro/Max only, not Team/Enterprise ([code.claude.com/docs/en/mobile](https://code.claude.com/docs/en/mobile)).

Attachment handling on Remote Control, per the official docs: **photos** are seen directly by Claude *and* saved to `~/.claude/uploads/` with the path told to Claude so it can reuse the file; **other files** are downloaded to the machine and passed as `@`-references. This is close to what AIOrchestrator's "file attachments policy" needs to define for its own bridge.

Claude Code also reached the iOS app in **October 2025** and Android **~March 2026** ([sealos.io](https://sealos.io/blog/claude-code-on-phone/); search summary), and "Claude Cowork" (multi-agent product surface) expanded to mobile/web per TechCrunch, **2026-07-07** ([TechCrunch](https://techcrunch.com/2026/07/07/the-coding-agent-wars-are-spilling-into-the-rest-of-the-office-claude-cowork/)).

### 1.2 Verified: Anthropic *did* ship official Telegram/Discord (and iMessage) channels in 2026

This directly answers the brief's open question. **Claude Code Channels** launched as a research preview on **2026-03-19/20** (VentureBeat dated 2026-03-19; MacStories hands-on dated 2026-03-20; other coverage puts the same week). ([VentureBeat](https://venturebeat.com/orchestration/anthropic-just-shipped-an-openclaw-killer-called-claude-code-channels); [MacStories](https://www.macstories.net/stories/first-look-hands-on-with-claude-codes-new-telegram-and-discord-integrations/); [Towards AI](https://pub.towardsai.net/claude-code-channels-message-your-ai-coding-agent-from-telegram-and-discord-2026-5f263ccc4b9c))

Mechanism, per VentureBeat's technical breakdown:
- A **Channel is an MCP server** that pushes events into a running Claude Code session. Launched with a `--channels` flag; runs on **Bun** as a polling service watching the messaging plugins.
- Inbound messages are injected into the session as a `<channel>` event; Claude replies through a dedicated **`reply` tool** back to the external platform.
- Sessions are designed to be **long-lived**: "can now run in a background terminal or a persistent server (like a VPS), waiting for a 'ping' to spring into action" — i.e., the same "always-on daemon woken by inbound traffic" shape as AIOrchestrator, but per-session rather than per-orchestration.
- Requires a **claude.ai Pro/Max subscription**; the Telegram/Discord plugins themselves are free and open source ([Towards AI](https://pub.towardsai.net/claude-code-channels-message-your-ai-coding-agent-from-telegram-and-discord-2026-5f263ccc4b9c), 2026). iMessage support followed about a week later; Slack/WhatsApp were the most-requested next platforms as of that coverage.

Hands-on gaps, per MacStories (2026-03-20), matter directly for AIOrchestrator's design bets:
- **Images work, voice does not**: "you can send images to Claude Code using Telegram... but there is no support for voice messaging."
- **Permission prompts are a dead end in chat**: *"if Claude Code needs your permission for something, there's no way to grant it in Telegram."* The workaround Anthropic ships is either go to the Mac terminal, or run with `--dangerously-skip-permissions`. Chunking strategy, multi-session navigation, and notification-noise handling are **not documented** — the reviewer didn't find or mention them, so treat those as **[unverified]** gaps in the official product, not confirmed absences.

This is the single most important competitive fact for AIOrchestrator: Anthropic validated "message your coding agent from Telegram" as a real, demanded surface within four months of this repo's design doc — but shipped it **without a structured approval mechanism** (no inline-button yes/no, no "ask the owner" schema) and without multi-orchestration/topic-per-project navigation. AIOrchestrator's forum-topics-per-orchestration + inline-keyboard "ask the owner" design is not a redundant reinvention; it is the part official Channels visibly lacks.

### 1.3 The rest of the field

**OpenAI / Codex.** Codex reached the ChatGPT mobile app (iOS/Android) on **2026-05-14**, for all plans including Free/Go in supported regions. On mobile you approve decisions, review diffs, redirect running tasks, and watch terminal output; pairing with a desktop session is via **QR code**, and at launch only macOS hosts are supported (Windows pending). Runs isolated cloud sandboxes; pauses for human decisions, resumes on reply. Reported >4M weekly users **[unverified date on the figure]**. ([buildfastwithai.com](https://www.buildfastwithai.com/blogs/openai-codex-mobile-chatgpt-app-2026); [pasqualepillitteri.it, dated "May 2026"](https://pasqualepillitteri.it/en/news/2564/codex-chatgpt-mobile-vs-claude-code))

**Cursor.** Background Agent (cloud VM, own repo checkout) expanded through 2026; reachable at **cursor.com/agents** on web and via iOS/Android apps, plus Slack pairing so a backlog item can already be a draft PR by the time you sit down. **February 2026**: "Cloud Agents with Computer Use" — full desktop/browser environment per agent, plus **recorded video demos** of the agent's work so reviewers watch a 30-second clip instead of reading a diff — a genuinely different answer to "how do you review long output on a phone." Mobile apps are explicitly **chat + result-surfacing only, "no editing surface."** >30% of Cursor's own internally-merged PRs now come from cloud agents. ([DeployHQ guide](https://www.deployhq.com/guides/cursor); [Geekflare](https://geekflare.com/news/you-can-now-use-cursor-agents-on-the-web-and-your-phone/); [Cursor forum announcement](https://forum.cursor.com/t/introducing-cursor-on-web-mobile/111183))

**Omnara.** A dedicated cross-platform "command center" (iOS/Android/web/**Apple Watch**) for Claude Code and Codex: monitor, steer, approve from the phone; **Conversational Voice Mode** for two-way voice while commuting; "Seamless Cloud Handoff" preserving uncommitted code even if the laptop goes offline. Purpose-built native app, not a terminal wrapper. ([omnara.com](https://www.omnara.com/resources/mastering-remote-agent-tasks-developers-tool); [Apple App Store listing](https://apps.apple.com/us/app/omnara-claude-codex-mobile/id6748426727))

**Happy Coder (slopus/happy).** Free, open-source, wraps the Claude Code / Codex CLI and relays its I/O (E2E-encrypted through a relay server) to iOS/Android/web. Adds **push notifications and voice input** that Anthropic's own Remote Control lacked at comparison time; multi-agent, not Claude-only. ([GitHub slopus/happy](https://github.com/slopus/happy); [happy.engineering](https://happy.engineering/))

**OpenClaw (formerly Clawdbot → Moltbot).** A fundamentally different bet: a **self-hosted, always-on personal agent** reachable over WhatsApp, Telegram, Slack, Signal, etc., that takes real-world actions (shell, browser, calendar, email, files) on a heartbeat scheduler, not just coding. Built by Peter Steinberger, launched under its earlier names in **late January 2026**, crossed **100,000 GitHub stars in under a week** — one of the fastest-growing repos in GitHub history. MIT-licensed, local-first (Markdown on disk for memory — structurally close to AIOrchestrator's own channel-files-as-memory bet), extensible via a portable "skill" format. Renamed OpenClaw after Anthropic trademark pressure on "Clawdbot." ([CNBC, 2026-02-02](https://www.cnbc.com/2026/02/02/openclaw-open-source-ai-agent-rise-controversy-clawdbot-moltbot-moltbook.html); [DataCamp](https://www.datacamp.com/tutorial/moltbot-clawdbot-tutorial))

**Community claude-code-telegram bots.** A cluster of independent open-source Telegram↔Claude-Code bridges (`RichardAtCT/claude-code-telegram`, `seedprod/claude-code-telegram`, `Angusstone7/claude-code-telegram`, `linuz90/claude-telegram-bot`, `pavel-molyanov/telegram-ai-agent`) predate Anthropic's official Channels and generally go further on the phone-console fundamentals: voice-message transcription, git integration, quick-action buttons, multi-format session export, SQLite persistence, Docker one-liner deploys, session resumption. These are the closest structural precedent to AIOrchestrator's own bridge, and confirm the "single VPS, one bot, file-backed state" shape is a well-worn, workable pattern, not a novel risk. ([GitHub listing search](https://github.com/RichardAtCT/claude-code-telegram))

**Devin in Slack (Cognition).** Tag `@Devin` in any channel/thread; it responds in-thread with updates/questions; accepts **voice clips via Slack's native recorder**. Devin 1.2 (2026) improved in-context reasoning for handling/reusing code. ([VentureBeat](https://venturebeat.com/ai/devin-1-2-updated-ai-engineer-enhances-coding-smarter-in-context-reasoning-voice-integration); [Fastio](https://fast.io/resources/devin-ai-slack-integration/))

**Claude Tag (Anthropic, Slack).** Announced **2026-06-23** (Bloomberg), replacing the older "Claude in Slack" app (retired **2026-08-03**). A persistent, memory-accumulating team member: tag `@Claude`, it plans multi-stage work, acts across connected tools, replies in-thread, and can **act proactively** (e.g., surface alerts) with preset guidance. Beta on Enterprise/Team plans only — i.e., not aimed at a solo owner. Anthropic reports 65% of its own product-team code now flows through the internal version. ([Bloomberg, 2026-06-23](https://www.bloomberg.com/news/articles/2026-06-23/anthropic-wants-claude-to-be-your-new-slack-coworker); [Anthropic news](https://www.anthropic.com/news/introducing-claude-tag))

### 1.4 Medium-by-medium comparison

| Medium | Message limit | Delivery model | Structured decisions | Threading/grouping | Fit for 1-owner, N-orchestration console |
|---|---|---|---|---|---|
| **Telegram Bot API** | 4096 chars/message [documented, core.telegram.org/bots/api] | `getUpdates` long-poll (single consumer per token) or webhook; both deliver, never both at once — updates retained 24h server-side if undelivered ([conferbot.com limits page](https://www.conferbot.com/limits/telegram); [core.telegram.org/bots/api](https://core.telegram.org/bots/api)) | Inline keyboards + `reply_markup` — native, mature | **Forum topics** — one thread per project/orchestration, purpose-built | Best fit already built: rate limits (1 msg/s per chat, **20 msg/min per group**, ~30 msg/s bulk across chats) are generous for one human's cadence; forum topics map 1:1 to orchestrations |
| **Discord** | 2000 chars plain content; **Components V2** (since April 2025) allows richer stacked layouts, 40 components/message; embeds up to 10 objects, 6000 chars combined | Gateway (bots) + webhooks; 50 req/s global bot rate limit ([space-node.net](https://space-node.net/blog/discord-api-changes-whats-new-2026); [dweeb.faizo.net Components V2 guide](https://dweeb.faizo.net/guides/discord-components-v2/)) | Buttons/selects via Components V2 — arguably richer than Telegram's inline keyboards now | Forum/media channels need `thread_id` or `thread_name` per post — same shape as Telegram topics, more setup | Comparable technically, but no existing owner presence/workflow here; would be a rebuild for no material gain |
| **Slack** | ~4000 chars recommended, hard truncate ~40,000; Block Kit: 3000 chars/section block, 50 blocks/message ([GitHub slackapi/bolt-js issue #2509](https://github.com/slackapi/bolt-js/issues/2509); [conferbot.com](https://www.conferbot.com/limits/slack)) | Events API/Socket Mode + threads; **Assistants API** (2025-26) formalizes agent-in-thread UX — this is what Claude Tag and Devin ride on | Block Kit is the richest structured-UI option of the three | Threads, channels | Best structured UI, but workspace-oriented, heavier to stand up for a single owner, and Anthropic's own Claude Tag targets Enterprise/Team, not solo |
| **Self-hosted PWA + Web Push** | No message-size ceiling — you own the rendering | VAPID web push; own subscriber list, own DB — full control ([WordPress plugin listing](https://wordpress.com/plugins/push-notification) as a generic reference for the pattern) | Whatever you build | Whatever you build | Maximum flexibility, but you inherit auth, offline delivery reliability, and cross-device sync yourself — a second product to maintain |
| **MTProto userbot** | No 4096 cap; arbitrary `messages.getMessages` by ID, no HTTP hop | Direct MTProto connection, no Bot API intermediary — less overhead ([Telethon docs, botapi-vs-mtproto](https://docs.telethon.dev/en/v2/concepts/botapi-vs-mtproto.html); [mtcute.dev](https://mtcute.dev/guide/intro/mtproto-vs-bot-api)) | Build-your-own | Build-your-own | Removes the Bot API's real but *already-solved* constraints (single poller, 4096 cap) at the cost of running under a personal account, ToS ambiguity, and materially more engineering — not worth it for this product |
| **iOS/Android native** | N/A | Full native UX, push via APNs/FCM | Full native UX | Full native UX | Best long-term UX, but a whole separate app to build and ship (see Omnara/Happy as the "someone already built this" answer) |

### 1.5 Recommendation

**Telegram + forum topics is the right medium for AIOrchestrator, and Anthropic's own March 2026 Channels launch is independent evidence for that call** — the same medium, the same "MCP-server-style event injection into a persistent session" shape AIOrchestrator already uses for the bridge. The gap is not the medium; it's finishing what Anthropic's own version conspicuously lacks:

1. **Structured "ask the owner" is the differentiator, not a nice-to-have.** Anthropic Channels has no way to grant a permission prompt from chat at all — its only escapes are the terminal or `--dangerously-skip-permissions`. AIOrchestrator's inline-keyboard approvals (already in the design) is a genuine, verified edge over the vendor's own product as of 2026-03.
2. **Add a Telegram Mini App as the read-side dashboard, not a replacement for chat.** Mini Apps in 2026 gained full-screen layouts, landscape, home-screen shortcuts, and richer data views ([clickgram.io](https://clickgram.io/blog/what-are-telegram-mini-apps/); [magnetto.com](https://magnetto.com/blog/everything-you-need-to-know-about-telegram-mini-apps)) — enough to render a real multi-orchestration grid (status, cost, worktree, last activity) launched from the bot's menu button, with zero extra install and no separate PWA/auth stack to maintain. Keep chat for the write path (decisions, questions) and use the Mini App purely for "what's the state of everything right now" — exactly the view a chat scrollback is bad at.
3. **Keep editing one message instead of stacking (already decision #14) and extend the pattern** to a pinned per-orchestration status message, refreshed on state change, so the phone never needs to scroll to answer "is this one done."
4. **Keep the single-poller constraint as a design invariant, not a risk to route around.** The Bot API's `getUpdates`-vs-webhook exclusivity and one-consumer-per-token limit are exactly matched by the app's role as the sole bridge process — no MTProto userbot, no second poller, is needed; the "single bot token" constraint is a feature here (it forces exactly the centralization the app already assumes).
5. Do **not** chase Discord or Slack for this product: both are technically comparable or richer (Slack's Block Kit, Discord's Components V2), but neither buys anything Nathan doesn't already have in Telegram, and each is a second platform's auth/rate-limit/dead-letter model to maintain for a one-owner console.

## QUESTION 2 — Agent↔agent and agent↔app transport and state

### 2.1 How comparable systems actually do it in 2025–2026

**Claude Code Agent Teams (Anthropic, shipped 2026-02-05 alongside Opus 4.6)** — the closest structural sibling to AIOrchestrator's own channel-file bus, and *verified*, not inferred: "the entire multi-agent system is JSON files on disk with no database, no message broker, or IPC — agents communicate by writing to each other's inbox files." Concretely: `~/.claude/teams/session-[id]/inboxes/*.json`, **one mailbox file per agent**, peer-to-peer (unlike ordinary subagents, teammates talk directly to each other, not only back to a parent). Critically: **Claude Code validates every entry as it reads the mailbox — malformed entries are reported and dropped, valid ones still delivered.** ([search summary of multiple 2026 write-ups, e.g. claudecodecamp.com, matthewswong.com](https://www.claudecodecamp.com/p/claude-code-agent-teams-how-they-work-under-the-hood)) This is direct validation of AIOrchestrator's own file-mailbox bet, and it names the one hardening step worth borrowing explicitly: **validate-on-read with drop-not-crash for malformed entries**, rather than trusting the channel file's shape.

**Anthropic's multi-agent research system (engineering blog, referenced widely through 2026 write-ups).** Orchestrator-worker pattern: a **lead agent** plans and spawns subagents with independent context windows; the lead's own state is preserved through a **memory mechanism that survives 200k-token context overflow**. Two file-system practices stand out and map onto AIOrchestrator's own vocabulary: (a) subagents **periodically summarize milestones to external memory** rather than replaying full history, and (b) subagents **write large outputs directly to the filesystem and pass back only a file reference/link**, never the payload itself. Reported result: +90.2% over single-agent Opus 4 on research tasks, at **~15× the token cost** of a normal chat call ([ZenML LLMOps DB summary](https://www.zenml.io/llmops-database/building-a-multi-agent-research-system-for-complex-information-tasks); [bytebytego summary](https://blog.bytebytego.com/p/how-anthropic-built-a-multi-agent)). The "pass a file reference, not the payload" discipline is exactly what a supervisor↔implementer channel file should also do for large diffs/logs — never paste them inline into the channel, append a path.

**Google A2A (Agent2Agent).** Announced **2025-04-09** at Google Cloud Next, contributed to the **Linux Foundation** June 2025, Apache-2.0. Defines **Agent Cards** (capability advertisement), **Tasks** (unit of exchanged work), and a transport of **HTTP + Server-Sent Events + JSON-RPC 2.0**, with OAuth2 for mutual auth. By **April 2026**, 150+ organizations support it (Google, Microsoft, AWS, Salesforce, SAP, ServiceNow, Workday, IBM), and it's natively integrated into Azure AI Foundry, Amazon Bedrock AgentCore, and Google Cloud. ([Google Developers Blog](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/); [A2A Wikipedia](https://en.wikipedia.org/wiki/Agent2Agent); [a2a-protocol.org](https://a2a-protocol.org/latest/)) A2A targets **cross-organization, network-addressable, opaque agents discovering each other** — a different problem than two Claude Code CLI processes on one VPS that already know each other's paths.

**MCP's relationship to agent-to-agent traffic.** MCP was donated to the Linux Foundation's new **Agentic AI Foundation (AAIF)** in **December 2025**; by March 2026 it reports 97M+ monthly SDK downloads and 81k+ GitHub stars, supported by every major vendor. Its own 2026 roadmap frames MCP as **Agent↔Tool**, with **A2A as the complementary Agent↔Agent layer**, and only in H2 2026 does the roadmap start talking about "agent-to-agent coordination maturing" *through* MCP Server Cards/discovery — i.e., MCP is not itself an agent-to-agent bus today, and Anthropic's own Claude Code Channels (§1.2) confirms this by using MCP purely as the **inbound event-injection mechanism into one agent**, not as agent↔agent transport. ([blog.modelcontextprotocol.io 2026 roadmap](https://blog.modelcontextprotocol.io/posts/2026-mcp-roadmap/); [dev.to MCP vs A2A guide](https://dev.to/pockit_tools/mcp-vs-a2a-the-complete-guide-to-ai-agent-protocols-in-2026-30li))

**OpenAI Symphony.** An open-sourced orchestration *spec* (not primarily a runtime) that turns **Linear** into the control plane: every open ticket gets an agent, and — the load-bearing design decision — **Linear itself is the durable source of truth, with no database in the orchestration layer**. On restart, Symphony rescans the board, finds tickets it owns that are "In Progress," and resumes; the state machine lives only in the board's own state, checked back into the system of record on every transition. Reported 500% more merged PRs internally at OpenAI. ([Better Stack guide](https://betterstack.com/community/guides/ai/openai-symphony/); [OpenAI blog](https://openai.com/index/open-source-codex-orchestration-symphony/); [MindStudio](https://www.mindstudio.ai/blog/openai-symphony-spec-linear-agent-control-plane-500-percent-pr-increase)) This is the cleanest real-world precedent for "treat the external, human-readable record as the actual database" — directly analogous to what PLAN.md is trying to be for AIOrchestrator, except Symphony's "database" (Linear) is queryable and has real schema, while PLAN.md is LLM-authored prose being parsed after the fact.

**Gas Town / Beads (Steve Yegge).** Gas Town is a multi-agent orchestrator (20–30 concurrent coding agents across Claude Code, Copilot, Codex, Gemini) built on **Beads**, his separate memory/issue system: each unit of work is a **"bead"** — a versioned record with title/description/status/links — stored in a **Git + SQLite backend**, so it is simultaneously **git-versioned** (diffable, auditable, mergeable) and **SQL-queryable** (structured, joinable across a "multi-graph" of related beads), explicitly pitched as "coding agent memory." ([ianbull.com](https://ianbull.com/posts/beads/); [DoltHub blog](https://www.dolthub.com/blog/2026-01-15-a-day-in-gas-town/); [GitHub gastownhall/beads](https://github.com/gastownhall/beads)) This is the strongest available precedent for "keep the audit trail of a plain-text VCS *and* get real query semantics," which is precisely the gap between AIOrchestrator's current PLAN.md (prose, VCS-tracked, not queryable) and what decisions #12/#13/#22 are already fighting to simulate by hand (untrusted headers, non-monotonic counts, section-based parsing to keep PARKED items out of the ledger denominator).

**Paperclip.** A newer (launched **2026-03-04**) open-source, MIT, self-hosted orchestrator modeling a team of agents as a company org chart; technically a **Node.js server + React dashboard backed by PostgreSQL**, no managed cloud offering. Crossed ~70k GitHub stars by June 2026; latest release v2026.831.1 (2026-09-02). ([Ry Walker research writeup](https://rywalker.com/research/paperclip); [AIToolTier review](https://aitooltier.com/tools/paperclip)) Structurally this is the "just use a real relational database, no files" answer — useful as a data point that a from-scratch, DB-backed alternative exists and is popular, but it trades away the file approach's two most valuable properties (grep-ability, works with the app process entirely down) for a conventional server+DB architecture.

**OpenHands EventStream.** The clearest formal articulation of **event sourcing for agent state** in this space: the whole system is "a function from event history to next event, run in a loop." A stateless `Agent` emits `Action`s; a `Conversation` runs the loop and persists an **append-only `EventLog`**; a `Workspace` executes actions and returns `Observation`s. The event system's four jobs, per the docs, are: type safety (Pydantic-schema'd events), LLM-format conversion, **append-only log**, and pub/sub service integration — and the SDK explicitly targets **deterministic replay**. ([docs.openhands.dev/sdk/arch/events](https://docs.openhands.dev/sdk/arch/events); [arXiv 2511.03690, OpenHands Software Agent SDK](https://arxiv.org/pdf/2511.03690)) This is the pattern that most directly generalizes AIOrchestrator's markdown channel: same append-only shape, but **typed and schema-validated** instead of free-text-with-conventions, which is exactly what would prevent decision #12's untrusted-header problem at the source.

**LangGraph checkpointers.** `SqliteSaver` persists graph state to a local file, survives process restarts, fine for single-process/local use; `PostgresSaver` additionally supports **multiple workers reading/writing the same checkpoint store**, i.e., horizontal scale-out. State is saved **after every node execution**, not just at the end, so a crash mid-turn resumes from the last completed step rather than replaying or losing it. ([LangChain docs, persistence](https://docs.langchain.com/oss/python/langgraph/persistence); [Fastio LangGraph persistence guide](https://fast.io/resources/langgraph-persistence/)) The granular per-step checkpoint (vs. per-turn) is finer-grained than anything AIOrchestrator currently does and is the concrete mechanism behind decision #10's "a fresh turn is told what is pending" work already merged in this repo (`3537d57`) — same problem, different implementation.

**Temporal / durable execution.** Workflows automatically capture state at every step; on failure, resume exactly where they left off, no manual recovery. Temporal's **official OpenAI Agents SDK integration reached GA on 2026-03-23**; OpenAI itself runs Temporal in production for agentic workloads at scale, alongside NVIDIA (long-running GPU workflows), Gorgias, ZoomInfo. ([Temporal blog](https://temporal.io/blog/durable-execution-meets-ai-why-temporal-is-the-perfect-foundation-for-ai); [Temporal AI solutions page](https://temporal.io/solutions/ai)) Temporal is the "buy a real durable-execution engine" end of the spectrum — powerful, but it's a standing service dependency (a Temporal cluster or Temporal Cloud) that must itself be running, which directly conflicts with AIOrchestrator's own valued property of "works with the app down" (decision #3's design goal, and the whole reason channel files exist instead of a service).

**CrewAI vs AutoGen message passing.** AutoGen uses **broadcast/pub-sub group-chat**: agents post into a shared conversational channel, and an LLM-driven manager picks the next speaker; the developer defines the conversation topology (who can address whom, in what order). CrewAI is **role-based** and explicitly **does not give agents a direct messaging channel** — coordination happens only through task *outputs* being handed downstream, which is more constrained/predictable but less expressive. ([ZenML CrewAI vs AutoGen](https://www.zenml.io/blog/crewai-vs-autogen); [LogRocket comparison](https://blog.logrocket.com/autogen-vs-crew-ai/)) AIOrchestrator's hub-and-spoke design (decision #4: each implementer has its own duplex channel with the supervisor, implementers never see each other) sits structurally closer to CrewAI's "no direct peer messaging, everything through the hub" model than to AutoGen's group chat — which is a **deliberate and, per this comparison, well-precedented choice**: it trades away possible agent-to-agent negotiation for predictability and a single reviewer choke-point, which matches the product's supervisor-gates-everything philosophy.

**NATS / Redis Streams / Kafka (local event bus options).** 2026 benchmark figures cited: Redis Streams ~0.8ms p99, NATS JetStream ~3.2ms, Kafka ~12.5ms end-to-end latency; NATS JetStream is favored for Kubernetes-native microservice fan-out, Redis Streams for low-latency moderate-volume pub/sub. ([dev.to Kafka vs Redis Streams vs NATS 2026](https://dev.to/young_gao/real-time-event-streaming-kafka-vs-redis-streams-vs-nats-in-2026-34o1)) None of these numbers matter at human/agent conversational cadence (seconds, not milliseconds); their real cost for AIOrchestrator would be operational — a broker process to run, monitor, and keep alive, directly undermining "works with the app down."

### 2.2 Comparison table

| Approach | Durability | Ordering | Ack/idempotency | Human-readable | Works with daemon down | Parsing ease | Replay/debug |
|---|---|---|---|---|---|---|---|
| **AIOrchestrator today** (markdown + byte-offset tail + JSON request files + prose PLAN.md) | High (plain files, git-friendly) | Append order only, no sequence numbers | None built-in — request files are the closest thing to idempotency | Excellent (this is the whole point) | Yes, fully | Fragile — free text, agent-written headers untrusted (decision #12) | Good for "what happened," weak for "what's the current count/state" (decision #13) |
| **Claude Agent Teams mailbox** (JSON per-agent inbox, validated on read) | High (disk files) | Per-mailbox append order | Malformed entries dropped, not silently trusted | Medium (JSON, not prose) | Yes | Easy — schema-checked | Good — invalid entries are visibly rejected, not silently corrupting state |
| **OpenAI Symphony** (Linear as state machine) | High (external SaaS is system of record) | Board-state transitions | Restart = rescan board, natural idempotency | High (it's a normal issue tracker) | No — depends on Linear being reachable | Easy (structured issue fields) | Good — board state *is* the debug view |
| **Gas Town / Beads** (Git + SQLite) | High (git history + DB) | SQL-queryable, has real ordering/links | Possible via DB transactions | High (still greppable git-tracked text) | Yes | Easy — SQL | Excellent — queryable multi-graph, versioned |
| **OpenHands EventStream** | High (append-only log) | Strict, typed sequence | Schema-validated events | Medium (structured JSON events, not prose) | Depends on implementation (file or DB-backed) | Easy — typed events | Excellent — deterministic replay is a design goal |

### 2.3 Recommendation for a single-VPS, multi-session Claude Code orchestrator

Keep the file-based bus — the industry's own newest and closest precedent (Claude Code Agent Teams, Feb 2026) independently arrived at "JSON files on disk, no DB, no broker" for exactly this problem, and Symphony/Beads both preserve a human/greppable substrate even where they add structure. The fix AIOrchestrator needs is not a different transport, it's **separating narrative from state**, which is the one thing every stronger precedent above (Agent Teams' schema validation, OpenHands' typed event log, Symphony's structured board, Beads' SQL layer) does that plain prose markdown does not:

1. **Keep markdown channel files exactly as they are** for the human-facing narrative and the Telegram mirror — this property (auditable, greppable, survives daemon restart, no dependency to keep alive) is real and is what every DB/broker-based alternative above gives up.
2. **Add a machine-authoritative JSONL sidecar per channel**, one line per entry, written by the *daemon* (never trust the writing agent for the authoritative fields) with: a monotonic sequence number, the daemon's own UTC append timestamp (not the agent's self-reported one — this directly fixes decision #12's untrusted-header problem at the source rather than patching it downstream with `Describe_SinceStamp_OrNull`), author, byte-range in the markdown file, and entry kind. This is the OpenHands-style typed event log, sized down to what a single-owner VPS actually needs.
3. **Count and "has this been answered yet" logic reads only the JSONL sidecar**, never the live markdown file's line count — this directly fixes decision #13 (`Channel_Compactor` breaking a live-count check) by construction: the sidecar's sequence number is monotonic across compaction the way a raw line count never can be.
4. **Turn PLAN.md from LLM-authored prose parsed after the fact into a generated view over a small structured store** (SQLite is the pragmatic choice — file-based, zero ops, git-diffable if you also dump it, and exactly what Beads and Paperclip independently converged on for the same "need real state, not just an audit trail" problem). Each ledger line becomes a row with an explicit `owner_request_ref`, `status`, and `parked` flag; `PlanLedger_Parser`'s current job of textually detecting PARKED sections (decision #22) becomes a `WHERE parked = false` — a schema check instead of a heuristic.
5. **Make JSON request files idempotent by construction**: on processing, rename/move into a `processed/` (or append a `.done` sibling) so a daemon restart mid-request can never double-apply a `start-orchestration`/`close-orchestration`. This borrows Temporal's exactly-once philosophy without adopting Temporal itself — the operational cost of running a durable-execution cluster is not justified at this scale and would break "works with the app down."
6. **Do not adopt NATS/Redis/Kafka or A2A/MCP as the core local bus.** The benchmarked sub-millisecond latencies are irrelevant at human/agent conversational cadence; A2A's Agent Card discovery model targets cross-organization opaque agents, not two Claude Code processes on one box that already know each other's file paths; and MCP, by Anthropic's own 2026 roadmap and by Claude Code Channels' own implementation choice, is Agent↔Tool, not Agent↔Agent. None of these buy AIOrchestrator anything it doesn't already have, and all of them add a service dependency the file-based design specifically exists to avoid.

Net effect: the file bus stays the interface (nothing about the Telegram bridge, the watcher-wakeup pattern, or the audit trail changes), but every place PLAN.md or a channel file is currently asked to double as a database — a count, a status, a "has this been actioned" check — gets a real, schema-checked, daemon-authoritative answer instead of a text-parsing heuristic. That is the single highest-leverage change the 2025–2026 comparison set points to.
